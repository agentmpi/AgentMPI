## 1. MPI-2/MPI-3 One-Sided RMA (Remote Memory Access)

### 1.1 The two central abstractions: window and process group

An MPI *window* binds a memory region at each process to a group of processes; the window's group is the group of the communicator used to create it [Hoefler15, §2]. This yields two orthogonal forms of spatial isolation that are the load-bearing engineering property of the design: (i) processes outside the group cannot touch memory exposed inside the group, and (ii) memory not attached to a window cannot be touched remotely *at all*, even by group members [Hoefler15, §2]. Non-exposed memory cannot be corrupted by a remote process. This is what makes layered libraries on top of MPI RMA possible: a library can carve out its own window and not interfere with user code [Hoefler15, §2; HoeflerSnir11].

### 1.2 Window creation: four variants, four different purposes

| Call | Semantics | Why it exists |
|---|---|---|
| `MPI_Win_create(base, size, disp_unit, info, comm, &win)` | Each process exposes an arbitrary pre-existing contiguous region (size ≥ 0). Addressing is by *offset* from the target's window base, scaled by `disp_unit`. | The legacy MPI-2 call. Because each process may expose an arbitrary address, RDMA NICs may need large (possibly distributed) translation tables; remote lookups cost performance [Hoefler15, §2.1]. |
| `MPI_Win_allocate(size, disp_unit, info, comm, &baseptr, &win)` | MPI allocates the memory and returns the pointer. Otherwise identical to `Win_create`. | Lets the implementation use a *symmetric heap* — identical base addresses on all ranks — reducing per-peer metadata from O(p) to O(1) [Hoefler15, §2.1; Gerstenberger13]. foMPI implements symmetry either via a system-wide symmetric heap or a randomized `mmap` retry loop costing O(1) memory and O(log p) time w.h.p. [Gerstenberger13, §2.2]. |
| `MPI_Win_create_dynamic(info, comm, &win)` + `MPI_Win_attach` / `MPI_Win_detach` | Creates a window that exposes *no* memory; binds only a process group. Regions are attached later by local calls. Addressing is by absolute virtual address, not offset. | For programs whose exposed set changes at runtime: growable hash tables, object graphs, garbage-collected or OO runtimes. Cheaper conceptually but may be *more* expensive than allocated windows, since MPI must maintain per-region structures [Hoefler15, §2.1]. |
| `MPI_Win_allocate_shared(size, disp_unit, info, comm, &baseptr, &win)` + `MPI_Win_shared_query` | Maps the window into the address spaces of other processes in the (shared-memory-capable) communicator, so peers may use *direct load/store* in addition to RMA. | Exploits multicore nodes: intra-node peers get raw pointers instead of message-passing. Each process independently picks its local size; layouts need not be uniform [Hoefler15, §2.1, Fig. 3]. Usually paired with `MPI_Comm_split_type(comm, MPI_COMM_TYPE_SHARED, ...)`. |

### 1.3 Communication operations and exactly what is atomic

All RMA communication operations are **nonblocking** — they may return before completion — and are completed only by a subsequent synchronization or (for the `MPI_R*` request-based variants) by `MPI_Wait`/`MPI_Test` [Hoefler15, §1.2, §2].

- `MPI_Put`, `MPI_Get` — bulk data movement. **No atomicity whatsoever.** Concurrent puts from several origins to the same target location have *undefined* result; so does a single origin issuing multiple puts to the same location within one access epoch. The standard is explicit that the target "may have all of the data from one of the put operations (the 'last' one, in some sense), some bytes from each of the operations, or something else" [MPI41, §13.7]. Put and get within an epoch are also **unordered** [MPI41, §13.7.2].
- `MPI_Accumulate(origin_addr, origin_count, origin_dt, target_rank, target_disp, target_count, target_dt, op, win)` — combine-into-target using a *predefined* `MPI_Reduce` operator (user-defined ops are forbidden), plus the extra operator `MPI_REPLACE` (f(a,b)=b). All datatype arguments must be built from the *same* predefined base type; the operator applies to elements of that base type [MPI41, §13.3.4.1].
- `MPI_Get_accumulate(...)` — fetch-then-accumulate; returns the pre-accumulation target content in a result buffer disjoint from the origin buffer. Adds operator `MPI_NO_OP` (f(a,b)=a), giving an atomic read. "The operation is executed atomically for each basic datatype" [MPI41, §13.3.4.2].
- `MPI_Fetch_and_op(origin_addr, result_addr, datatype, target_rank, target_disp, op, win)` — the single-element special case of get-accumulate, carved out specifically so implementations can map it onto hardware fetch-and-add/fetch-and-increment. `datatype` must be predefined. "The operation is executed atomically" [MPI41, §13.3.4.3].
- `MPI_Compare_and_swap(origin_addr, compare_addr, result_addr, datatype, target_rank, target_disp, win)` — atomic CAS on one element; `datatype` restricted to C integer, Fortran integer, Logical, Multi-language, or Byte [MPI41, §13.3.4.4].

**The precise atomicity guarantee.** MPI-4.1 §13.7.1: "The outcome of concurrent accumulate operations to the same location with the same predefined datatype is as if the accumulate operations were done at that location in some serial order. ... Thus, there is no guarantee of atomicity beyond element-wise atomicity." Consequences: (a) atomicity is *per basic element*, not per operation; a 1000-element `MPI_Accumulate` is 1000 independent atomic updates, not one; (b) "The outcome of accumulate operations with overlapping types of different sizes or target displacements is undefined"; (c) different interleavings can differ only because floating-point arithmetic is not associative [MPI41, §13.7.1]. Additional restrictions may be requested via the window info key `accumulate_ops` (`same_op` / `same_op_no_op`).

**Ordering of accumulates** is separately specified and is *stronger* by default than in MPI-2: strict ordering (rar, raw, war, waw) between accumulate operations from the *same origin* to *overlapping* locations at the *same target*, relaxable via the window info key `accumulate_ordering` (comma-separated subset, or `none` for MPI-2 behaviour). "MPI does not provide any guarantees for accesses or updates from different origin processes to overlapping target memory regions" [MPI41, §13.7.2]. This origin-local-only ordering is the crucial asymmetry: MPI orders *your* accumulates against each other and refuses to order them against anyone else's.

MPI deliberately does not provide fine-grained mutexes. The standard's own rationale: "RMA does not define fine-grained mutexes in memory (only logical coarse-grained window locks). MPI provides the primitives (compare and swap, accumulate, send/receive, etc.) needed to implement high-level synchronization operations" [MPI41, §13.5].

### 1.4 Epochs: the exact definitions

These two definitions are the technical core of the chapter and I quote them because paraphrase loses the asymmetry.

> "RMA communication calls with argument `win` must occur at an origin process only within an **access epoch** for `win`. Such an epoch is opened with an RMA synchronization call on `win`; it proceeds with zero or more RMA communication calls ... on `win`; it is closed with another synchronization call on `win`." [MPI41, §13.5]

> "In active target communication, a target window can be accessed by RMA operations only within an **exposure epoch**. Such an epoch is opened and closed by RMA synchronization calls executed by the target process." [MPI41, §13.5]

Structural rules: distinct access epochs for the same `win` at the same process must be disjoint; epochs on *different* windows may overlap. Distinct exposure epochs at a process on the same window must be disjoint but may overlap with exposure epochs on other windows and with access epochs on any window. There is a **one-to-one matching** between access epochs at origins and exposure epochs at targets: operations issued in one access epoch land in one exposure epoch iff they were issued in that access epoch. **In passive target mode there is no exposure epoch at all** — the target executes no synchronization calls [MPI41, §13.5].

### 1.5 Synchronization: three mechanisms

**(1) Fence (active target, collective).** `MPI_Win_fence(assert, win)` opens and closes both an access epoch and an exposure epoch over the whole window group. Suited to loosely-synchronous bulk-synchronous phases, or when the communication graph changes every iteration or is dense [MPI41, §13.5].

**(2) PSCW / general active target (pairwise).** `MPI_Win_post(group, assert, win)` and `MPI_Win_wait(win)` open/close the *exposure* epoch at the target, with `group` naming the expected origins. `MPI_Win_start(group, assert, win)` and `MPI_Win_complete(win)` open/close the *access* epoch at the origin, with `group` naming the targets. Post→start synchronization tells the origin the window is exposed; complete→wait tells the target the origin is done [MPI41, §13.5, §13.7]. Crucially the standard permits **weak synchronization**: `start` may return before the target's exposure epoch opens, and `put`/`complete` may return before it opens if data is buffered. The calls order *window accesses*; they do not necessarily synchronize anything else [MPI41, §13.5, Figs. 28–29]. `MPI_Win_test` gives a nonblocking `wait`.

**(3) Lock / passive target.** `MPI_Win_lock(lock_type, rank, assert, win)` with `lock_type ∈ {MPI_LOCK_EXCLUSIVE, MPI_LOCK_SHARED}` opens an access epoch to one target; `MPI_Win_unlock(rank, win)` closes it and does not return until operations issued in the epoch "have completed both at the origin and at the target." `MPI_Win_lock_all(assert, win)` opens a *shared* access epoch to **all** processes in the window; it is emphatically **not collective** — "the ALL refers to a lock on all members of the group of the window" [MPI41, §13.5.3]. Semantics of the lock types: exclusive-locked accesses "will not be concurrent at the window site with other accesses to the same window that are lock protected"; shared-locked accesses "will not be concurrent ... with accesses protected by an exclusive lock" [MPI41, §13.5.3]. Note this is a *window*-granularity logical lock, not a byte-range lock.

It is **erroneous** to have a window locked and exposed concurrently (e.g., locking a target that is between `post` and `wait`) — mutual exclusion between the two mechanisms is the user's job, and the Forum's rationale is that enforcing it would tax the common case where the mechanisms never interact [MPI41, §13.5.3]. Implementations may restrict lock-synchronized RMA to memory from `MPI_Alloc_mem`, `MPI_Win_allocate`, `MPI_Win_allocate_shared`, or `MPI_Win_attach`, because passive-target progress across shared-memory domains may need an asynchronous software agent that is far cheaper over specially allocated memory [MPI41, §13.5.3].

**Flushes (passive target only) — the MPI-3 addition that made passive target usable.** All of these may be called *only inside* a passive-target epoch [MPI41, §13.5.4]:

- `MPI_Win_flush(rank, win)` — outstanding operations to `rank` complete **at origin and at target**.
- `MPI_Win_flush_all(win)` — same, to all targets.
- `MPI_Win_flush_local(rank, win)` — operations complete **at the origin only**; "the user may reuse any buffers provided to put, get, or accumulate operations."
- `MPI_Win_flush_local_all(win)` — same, all targets.
- `MPI_Win_sync(win)` — in the separate model, synchronizes the private and public window copies at the caller. In the unified model, orders load/store accesses and makes stores visible to other threads/processes. It "does not open or close an epoch and does not complete any pending RMA operations," and "does not guarantee progress of any pending MPI operation" [MPI41, §13.5.4].

The `flush` / `flush_local` split — remote completion versus local buffer reuse — is exactly the distinction that lets an implementation avoid a round trip when all the caller needs is its buffer back. This separation is what makes MPI-3 RMA a viable OpenSHMEM backend: OSHMPI implements `shmem_put` as `MPI_Put` + `MPI_Win_flush_local`, and `shmem_quiet` as `MPI_Win_flush_all` + `MPI_Win_sync` [Si21].

### 1.6 The two memory models: `MPI_WIN_SEPARATE` vs. `MPI_WIN_UNIFIED`

The standard's model: there is a *public* memory region addressable by all processes, and *private* per-process buffers (caches, communication buffers) holding copies. If those buffers are coherent, all main-memory updates are reflected in all private copies; if noncoherent, conflicting accesses must be synchronized and propagated *explicitly*. "Coherent systems allow direct updates to remote memory without any participation of the remote side. Noncoherent systems, however, need to call RMA functions in order to reflect updates to the public window in their private memory." Hence: **RMA unified** if public and private windows are logically identical, **RMA separate** otherwise [MPI41, §13.4]. Query via the window attribute `MPI_WIN_MODEL`.

In the **separate** model there is one instance of each variable in process memory but a *distinct public copy per window containing it*. A load reads process memory; a local store updates process memory but may affect public copies; a get reads the window's public copy; a put/accumulate updates the public copy and may affect the private copy and public copies of other overlapping windows [MPI41, §13.4]. The visibility rules (§13.7, rules 5–6):

- private → public: at the latest on the owner's ensuing `MPI_Win_post`, `MPI_Win_fence`, `MPI_Win_unlock`, `MPI_Win_unlock_all`, or `MPI_Win_sync`.
- public → private: at the latest on the owner's ensuing `MPI_Win_wait`, `MPI_Win_fence`, `MPI_Win_lock`, `MPI_Win_lock_all`, or `MPI_Win_sync`.

In the **unified** model both directions happen *eventually without additional RMA calls*, which "allow[s] the user to omit some synchronization calls and potentially improve performance" [MPI41, §13.4].

Why the distinction exists at all: it is a direct hardware-coherence pass-through. Cache-coherent nodes and RDMA NICs that write into coherent memory give you unified; non-coherent accelerators/scratchpads and software-emulated coherence give you separate. MPI-2 had only the software-coherence mechanism; MPI-3 "defines a completely new memory model and access mode that can rely on hardware coherence instead of MPI-2's expensive and limited software-coherence mechanisms" [Hoefler15, §1.1].

Two traps worth carrying into a design document. First, unified is *not* sequentially consistent: "Updates from an origin process will appear in the memory of the target, but there are no atomicity or ordering guarantees if more than one byte is updated. Updates are stable in the sense that once data appears in the memory of the target, the data remains until replaced by another update. This permits polling on a location for a change from zero to nonzero or for a particular value, but not polling and comparing the relative magnitude of values" [MPI41, §13.7]. Second, `MPI_Barrier` gives *process* synchronization, not *memory* synchronization; the standard's own examples show a store-then-barrier-then-remote-get pattern producing stale data even in the unified model, because the compiler or hardware may sink the store past the barrier [MPI41, §13.7]. Boehm's "threads cannot be implemented as a library" result applies to MPI RMA too [Hoefler15, §1.1; Boehm05].

The separate model also carries a constraint that looks gratuitous and is not: a put/accumulate must not access a target window once a store, or a put/accumulate to another *overlapping* window, has started — **even if the locations are disjoint**. The Forum's rationale: on some architectures the coherence-restoring operation needed at a synchronization point differs for store-updated versus RMA-updated locations, so without this rule MPI would have to track precisely which locations were touched by RMA, and "the additional overhead of maintaining such information is considered prohibitive" [MPI41, §13.7].

### 1.7 Why MPI-2 RMA was considered unusable, and what MPI-3 changed

MPI-2 (1997) designed one-sided communication against the hardware of 1997. The retrospective judgement from the working group that rewrote it: "The MPI-2 abstract machine model does not reflect today's RDMA networks well and does not support the exploitation of RDMA's full potential, which inhibited its adoption" [Hoefler15, §1].

The sharpest external critique is Bonachea & Duell [Bonachea04]. Evaluating MPI as a compilation target for PGAS languages (UPC, Titanium, Co-Array Fortran), they concluded that "the MPI 2.0 one-sided API imposes a number of significant restrictions on memory access patterns that would need to be incorporated at the language level, as a compiler cannot effectively hide them given current conflict and alias detection algorithms," and that MPI-RMA "imposes too many semantic restrictions to be a useful portable compilation target, at least for parallel languages which allow aliasing, data conflicts and/or the illusion of a single, arbitrarily accessible shared address space" [Bonachea04]. They were careful that this is not a claim that MPI-RMA is useless — application programmers who can globally structure their code to obey the restrictions do fine — but that it cannot be a *substrate*.

Concretely, what MPI-3 fixed:

1. **Overlapping/conflicting accesses were reclassified from erroneous to undefined.** The standard's rationale cites Bonachea & Duell directly: requiring overlapping puts to be erroneous "makes it difficult to use MPI RMA to implement programming models — such as Unified Parallel C (UPC) or SHMEM — that permit these operations," and further, "while MPI-2 defined these operations as erroneous, the MPI Forum is unaware of any implementation that enforces this rule, as it would require significant overhead" [MPI41, §13.7]. Since MPI-3, implementations *must not* raise an error for such accesses.
2. **The unified memory model**, exposing hardware coherence rather than paying for software coherence [MPI41, §13.4; Hoefler15].
3. **`Win_allocate` and `Win_create_dynamic`**, for symmetric heaps and dynamic memory respectively [Hoefler15, §2.1].
4. **`Win_allocate_shared`**, giving direct load/store to intra-node peers.
5. **Real atomics**: `Get_accumulate`, `Fetch_and_op`, `Compare_and_swap` (MPI-2 had only `Accumulate`, i.e., no atomic read-modify-write returning the old value).
6. **`Lock_all` plus the flush family**, giving a long-lived shared-lock epoch with fine-grained completion instead of lock/unlock per operation.
7. **Request-based `MPI_Rput`/`Rget`/`Raccumulate`/`Rget_accumulate`**, for per-operation completion.
8. **Default strict accumulate ordering** (MPI-2's behaviour was `none`) [MPI41, §13.7.2].

Dinan et al. built the first complete MPI-3 RMA implementation (in MPICH 3.0.1) and measured the effect: the MPI-3 interface "provides significant advantages over the MPI-2 interface by enabling increased communication concurrency through relaxed semantics in the interface and additional routines that provide new window types, synchronization modes, and atomic operations" [Dinan16]. Gerstenberger et al.'s foMPI showed MPI-3 RMA can beat tuned two-sided MPI and match or beat UPC/CAF on Cray Gemini/Aries by interfacing directly to DMAPP and XPMEM, with O(1) window metadata for allocated windows and O(log p) fence [Gerstenberger13].

### 1.8 What MPI RMA borrowed from PGAS, and what it refused

Borrowed: the fundamental split of the address space into a local load/store-accessible part and a remote put/get-accessible part — "a viable middle ground" after the general conclusion that transparent shared memory cannot be emulated efficiently on distributed memory [Hoefler15, §1]. Borrowed from OpenSHMEM/CAF: symmetric allocation (`Win_allocate`), long-lived passive access (`Lock_all` ≈ SHMEM's always-open access), local-vs-remote completion (`flush_local` ≈ `shmem_fence`-ish, `flush` ≈ `shmem_quiet`), and atomics on remote memory [OpenSHMEM12; Si21]. Borrowed from CAF-2's *teams* proposal, itself modelled on MPI communicators, the notion of a scoped process group [Hoefler15, §1.1].

Refused:

- **A global address space.** There is no "shared pointer"; you address (target_rank, displacement). UPC and CAF give a two-level local/remote *view* of memory [Hoefler15, §1.1]; MPI never lets you dereference a remote address.
- **Language integration.** MPI-3 RMA is a library interface that "integrates easily into existing infrastructures ... [and] can work with all compilers" [Hoefler15, §1.1]. Global Arrays offers similar semantics but only for arrays [Nieplocha96]; X10 and Chapel offer higher-level abstractions that, per the MPI-3 working group's own assessment, "have yet to deliver the performance necessary in an HPC context" [Charles05; Chamberlain07; Hoefler15, §1.1].
- **Implicit synchronization.** MPI keeps completion, memory consistency, and process synchronization as three separately reasoned-about concepts [Hoefler15, §1.2]. PGAS models often fuse communication and synchronization for efficiency; MPI deliberately does not, at the cost of a harder programming model — the paper concedes the environment "is often not suitable for average programmers (e.g., domain scientists)" and is aimed at library writers [Hoefler15, §1.2].
- **Implicit exposure.** In UPC/SHMEM all shared/symmetric data is remotely reachable. In MPI you must explicitly attach memory to a window, and only the window's group can reach it.

## 3. Fault tolerance

### 3.1 The standard's posture: there isn't any

The exact language, unchanged from MPI-2.2 through MPI-3.1 [MPI22, §8.3; MPI31, §8.3]:

> "After an error is detected, the state of MPI is undefined. That is, using a user-defined error handler, or `MPI_ERRORS_RETURN`, does not necessarily allow the user to continue to use MPI after an error is detected. The purpose of these error handlers is to allow a user to issue user-defined error messages and to take actions unrelated to MPI (such as flushing I/O buffers) before a program exits. An MPI implementation is free to allow MPI to continue after an error but is not required to do so."

Combined with: "The error handler `MPI_ERRORS_ARE_FATAL` is associated by default with `MPI_COMM_WORLD` after initialization. Thus, if the user chooses not to control error handling, every error that MPI handles is treated as fatal" [MPI22, §8.3]. `MPI_ERRORS_ARE_FATAL` "causes the program to abort on all executing processes" (MPI-4.1 sharpens this to "abort all *connected* MPI processes") [MPI31, §8.3; MPI41, §9.3].

Gropp & Lusk's framing is the one to steal for a paper: fault tolerance "is not a property of MPI itself, since MPI is a specification of an API," nor of an implementation, "since no implementation can ensure that any program is immune from all faults"; it "is a property of an MPI program coupled with an MPI implementation" [GroppLusk04]. They also explicitly debunk the folk claim that MPI *requires* the job to die when a rank dies — that behaviour follows from the default error handler, chosen because "this would probably be the most useful default behavior, particularly for new users" [GroppLusk04].

### 3.2 FT-MPI (Fagg & Dongarra, 2000): recovery as a communicator property

FT-MPI attaches a *failure mode* to each communicator; a communicator in an error state can be repaired only by rebuilding it through a modified `MPI_Comm_{create,split,dup}` [Fagg00; Fagg02]:

- **ABORT** — graceful abort immediately on error detection; the user cannot trap it. To avoid it you must set every communicator to another mode.
- **BLANK** — failed ranks are not replaced; survivors keep their ranks; `MPI_COMM_WORLD` keeps its extent, with holes. Communicating with a hole is an invalid-rank error; `MPI_Comm_size` returns the *extent*, not the number of live processes.
- **SHRINK** — failed ranks are removed and the rank space is made contiguous; ranks change, so the application must re-call `MPI_Comm_rank`.
- **REBUILD** — failed processes are respawned to restore the original size; survivors keep their ranks. This is the default and best-tested mode, and exists for codes with structural size requirements (e.g., power-of-two FFT solvers).

Orthogonally, a *message* mode governs in-flight traffic: **CONT/CONTINUE** (operations that already returned `MPI_SUCCESS` finish properly unless the partner failed) or **NOOP/RESET** (all in-flight messages are dropped, on the assumption the app rolls back to its last consistent state) [Fagg00; FTMPIoverview]. Errors surface as `MPI_ERR_OTHER` from any MPI call, with details available through cached attributes [Fagg02].

The genealogy matters: FT-MPI's SHRINK is ULFM's `shrink`, its REBUILD is `shrink` + `spawn`, and its BLANK is the design ULFM deliberately dropped (holes make collectives and rank arithmetic a minefield).

### 3.3 ULFM (User Level Failure Mitigation)

ULFM's governing principle: "no MPI call (point-to-point, collective, RMA, IO, …) can block indefinitely after a failure, but must either succeed or raise an MPI error" [OMPI-ULFM]. The draft chapter states it as: "any MPI operation that involves a failed process must eventually either succeed or raise an MPI error"; "All MPI procedures must eventually return ... even if they involve a failed MPI process." It explicitly does **not** restore lost application data [ULFMdraft22].

New error classes: `MPI_ERR_PROC_FAILED` (an operation could not complete because a process failed), `MPI_ERR_PROC_FAILED_PENDING` (a potential sender for a wildcard `MPI_ANY_SOURCE` receive has failed; the receive itself is not cancelled), `MPI_ERR_REVOKED`.

**`MPIX_Comm_revoke(comm)` — the non-obvious one, and the reason ULFM is more than an error code.** MPI's failure notification is *non-uniform*: only processes that actually communicate with the dead rank learn of the failure. Bland et al. give the canonical deadlock: P₂ waits on a receive from P₃, P₃ on P₀, P₀ on P₁; P₁ has failed, and only P₀ detects it. P₀ must branch to a recovery path, but if it does, it stops posting the sends P₃ (then P₂, …) is waiting for, and the application deadlocks — "the messages that P₃ to Pₙ are waiting for will never [arrive]" [Bland13; FTHubRevoke]. `revoke` is the escape hatch: a *single* process calling it causes the communicator to become revoked at all non-failed members, after which every non-local operation on it raises `MPI_ERR_REVOKED` [Bland13; ULFMdraft22]. It has "a behavior similar to `MPI_ABORT` with the exception that it does not abort processes, instead it terminate[s] all ongoing operations on the communicator and mark[s] the communicator as improper for future communications" [Bland13]. Two properties to note: it is *not collective* and has no matching call; and there is no ordering guarantee between the revoke and local operations — "a receive operation can raise an error of class `MPIX_ERR_REVOKED`, even if the send operation procedure is called before the revoke procedure at the sender" [OMPI-ULFM]. Implementation: a reliable broadcast over a binomial-graph overlay with fixed maximum out-degree, giving logarithmic scaling [Bouteiller15; OMPI-ULFM changelog].

**`MPIX_Comm_shrink(comm, &newcomm)`** — collective, creates a new communicator excluding the failed group agreed upon during the operation, with ranks compacted to close gaps. Formally: `newcomm`'s groups must include every process that returns from the shrink and must exclude every process whose failure caused a `MPI_ERR_PROC_FAILED`/`_PENDING` at a member *before* that member initiated the shrink. It is "semantically equivalent to an `MPI_Comm_split` operation that would succeed despite failures," with all members using the same color and key = rank in `comm`. It never raises `MPI_ERR_REVOKED` or `MPI_ERR_PROC_FAILED` and **remains collective even on a revoked communicator** — that is what makes it the recovery entry point. It is best-effort about completeness: the new communicator may still contain processes whose failure is detected later [OMPI-ULFM]. `MPIX_Comm_ishrink` is the nonblocking form, with `MPI_Comm_idup`'s restriction that `newcomm` must not be used before the request completes.

**`MPIX_Comm_agree(comm, &flag)`** — this is a fault-tolerant *consensus*, not a reduction. It performs a reliable AND-reduction over `flag` on the survivors, "absorbs all new failures, and propagate[s] the knowledge about failures among the participants," and — the property that makes it consensus — "guarantees uniform failure reporting across the participating peers" [OMPI-ULFM; Losada20]. If a process fails before contributing, its contribution is ignored and `MPI_ERR_PROC_FAILED` is raised **consistently at all processes, in both local and remote groups**; if all processes had already acknowledged that failure, no error is raised at all [ULFMdraft22]. It never raises `MPI_ERR_REVOKED`, and it is collective even on a revoked communicator. Canonical uses: validating that an iteration or a collective succeeded everywhere, and validating a checkpoint commit [Losada20]. The pairing of `ack_failed` + `agree` in a loop until `MPI_SUCCESS` is the standard idiom for obtaining a *globally consistent* failed-process group [ULFMdraft22, Example 16.3].

**Failure acknowledgement.** In shipped Open MPI, `MPIX_Comm_failure_ack(comm)` acknowledges locally-notified failures (resuming `MPI_ANY_SOURCE` matching) and `MPIX_Comm_failure_get_acked(comm, &group)` returns the acknowledged-failed group [Losada20]. The current draft chapter renames and refines these to `MPI_COMM_GET_FAILED(comm, failedgrp)` — a *local* procedure returning the locally-known failed group, with a stability guarantee that a process in `failedgrp` stays at the same rank in later calls — and `MPI_COMM_ACK_FAILED(comm, num_to_ack, num_acked)`, which acknowledges the first `num_to_ack` failures by rank in that group and reports the cumulative count. Both are explicitly local: "It is possible that only the calling MPI process has detected the reported failure," and "MPI makes no assumption about asynchronous progress of the failure detection" [ULFMdraft22]. Acknowledging has no effect on collectives other than `agree`.

**Cost.** Agreement is the expensive primitive. The current state-of-the-art algorithm runs in 2·log_δ n parallel steps failure-free and at most O(2·log_δ n + fδ) with f failures, where δ is the max tree degree; ULFM's own literature warns that "the agree operation has a higher cost than an `MPI_Allreduce` operation and should, therefore, be used in a parsimonious manner" [Losada20]. Open MPI's changelog notes a "new algorithm to perform agreements, with a truly logarithmic complexity in number of ranks, which translates into huge performance boosts in `MPI_COMM_(I)AGREE` and `MPI_COMM_SHRINK`" — i.e., shrink's cost is dominated by the agreement inside it [OMPI-ULFM].

**Standardization status.** As of **MPI-5.0 (June 5, 2025), ULFM is still not in the ratified standard.** MPI-5.0's own summary of itself: "The largest change is the addition of a standard Application Binary Interface (ABI)" — no fault tolerance [MPI50, §2.10]. The Forum's Fault Tolerance WG (chairs Bouteiller and Laguna in the 5.0 cycle [MPI50, acknowledgements]) has been advancing ULFM in *slices*, with "slice 2: agree" and "slice 3: shrink" read at 2023 Forum meetings [MPIForum2023]. The specification document itself is labelled "Unofficial Draft for Comment Only" [ULFMdraft22]. Open MPI ≥ 5.0 ships ULFM built-in but inactive by default (`mpi_ft_enable`, default false; `--with-ft ulfm`), with `MPIX_` prefixes [OMPI-ULFM]. Which slices, if any, were adopted into MPI-5.0's text is `[UNVERIFIED]` — my check of the 5.0 change summary found no fault-tolerance mention, but I did not read the full 1000+ page document.

**Assessment.** Laguna et al. evaluated ULFM on a large bulk-synchronous molecular dynamics code (ddcMD) and concluded that "although ULFM is suitable for master–worker applications, it provides few benefits for more common bulk synchronous MPI applications," proposing instead **Reinit**: global, backward, non-shrinking recovery, in which the application wraps its main loop in a restart handler and the MPI runtime reinitializes to a post-`MPI_Init`-equivalent state and re-enters the handler with a start-state flag [Laguna16]. EReinit pushes the primitives down into the resource manager's node-process hierarchy, using local monitors instead of consensus-based detection [EReinit19] `[UNVERIFIED: full author list]`. The pattern is instructive: the *general* mechanism (revoke/shrink/agree, arbitrary recovery topology) lost to a *specialized* one (roll everything back, same ranks) for the dominant application class.

### 3.4 MPI-4 error handling improvements

MPI-4.0 added `MPI_ERRORS_ABORT`, a middle ground between "kill everything" and "return and hope": invoked on a communicator it acts like `MPI_Abort` on *that* communicator; on a window or file, like `MPI_Abort` on the group associated with it; **on a session, it aborts only the local MPI process** [MPI41, §9.3]. `MPI_ERRORS_ARE_FATAL` was also sharpened to "abort all *connected* MPI processes." Error handlers can now be attached to **sessions** (`MPI_Session_create_errhandler`, and an `errhandler` argument to `MPI_Session_init` itself — notable because it covers errors *during initialization*, which the world model could not) [MPI41, §9.3, §12.3.1]. MPI-4.1 also clarifies that windows and files do *not* inherit the initial error handler the way predefined communicators do [MPI41, §9.3]. None of this changes the "state of MPI is undefined" posture; it changes the blast radius.

### 3.5 Checkpoint/restart

**Coordinated vs. uncoordinated, and the domino effect.** Elnozahy et al.'s taxonomy [Elnozahy02] splits rollback recovery into checkpoint-based (uncoordinated / coordinated / communication-induced) and log-based (pessimistic / optimistic / causal message logging, where nondeterministic events are recorded as *determinants*). The failure mode of uncoordinated checkpointing: if a sender rolls back past the send of m, the receiver must roll back past the receipt of m, or the pair's states are inconsistent (a message received but never sent). "Under some scenarios, rollback propagation may extend back to the initial state of the computation, losing all the work performed before a failure. This situation is known as the **domino effect** [Randell 1975]" [Elnozahy02]. Coordinated checkpointing avoids it by construction (a consistent recovery line always exists) at the price of global synchronization; communication-induced checkpointing forces extra checkpoints to bound propagation; log-based recovery avoids it by replaying logged nondeterministic events, but requires the **piecewise-deterministic** assumption — each process's execution is a sequence of deterministic intervals, each begun by a nondeterministic event [Elnozahy02].

**Optimal interval — the actual formulas.** Young [Young74] derived τ_opt = √(2δM), where δ is the checkpoint write time and M the mean time to interrupt. Daly's first-order rederivation adds restart time R:

> τ_opt = √(2δ(M + R)),  for τ + δ ≪ M   [Daly06, Eq. 12]

and his higher-order (perturbation) solution — which shows R actually makes *no* contribution to the optimum — is:

> τ̃_opt = √(2δM) · [ 1 + (1/3)·√(δ/(2M)) + (1/9)·(δ/(2M)) ] − δ,  for δ < 2M;  τ̃_opt = M for δ ≥ 2M   [Daly06, Eq. 37]

guaranteeing that "the relative error in total problem-solution time ... never exceeds 0.2% of the exact solution" [Daly06, §6]. Daly's own recommended simple form (equivalent to Young's, error < 5% even at the worst case δ = M/2) is τ̃_opt = √(2δM) − δ for δ < M/2, else M [Daly06]. The exact solution is expressible via the Lambert W function but is useless as an engineering estimate [Daly06, Eq. 25].

**Multilevel / diskless / in-memory checkpointing.** The scaling argument: system memory grows faster than parallel-file-system bandwidth, so checkpoint cost comes to dominate runtime. SCR writes to node-local RAM/flash/disk in addition to the PFS, using cheap checkpoints for common failures and expensive ones for severe failures; measured low-cost schemes 100×–1000× faster than the PFS and effective against 85% of observed failures, yielding up to 35% machine-efficiency gain and halving PFS load; modelled with a probabilistic Markov model [Moody10; Moody14]. FTI integrates topology-aware Reed–Solomon encoding into a three-level scheme with a dedicated FT thread per node, achieving 8% checkpoint overhead on sustained 0.1 PFLOPS runs (1152 GPUs) at high frequency [BautistaGomez11]. VeloC targets asynchronous multilevel checkpointing with performance modelling and lightweight monitoring to pick local devices dynamically [Nicolae19]. BLCR-style transparent system-level checkpointing sits underneath these `[UNVERIFIED: I did not consult a primary BLCR source]`.

### 3.6 ABFT and replication

**ABFT** (Huang & Abraham 1984) encodes data at the algorithm level and redesigns the algorithm to operate on encoded data and produce encoded output. For matrices: row-, column-, and full-checksum matrices, where an n×m matrix A gains a checksum row and/or column. The checksum property is preserved by the operation, so a violation localizes the error — a single erroneous element sits at the intersection of an inconsistent row and column and can be corrected by solving from the checksums. Applied to addition, multiplication, scalar product, LU decomposition, and transposition; "can detect and correct any failure within a single processor in a multiple processor system" [Huang84]. The modern framing: ABFT is ECC for data *under transformation*, whereas ECC protects static data [Bosilca16abft].

**Replication vs. checkpointing.** Ferreira et al. evaluated state-machine replication as the *primary* exascale FT mechanism, arguing that checkpoint/restart overheads are "predicted to more than double an application's time to solution" at scale, and concluding via modelling, empirical measurement, and simulation across failure distributions, hardware MTTFs, and I/O bandwidths that replication "is a potentially useful technique for meeting the fault tolerance demands of HPC applications on future exascale platforms" [Ferreira11]. Their rMPI library implements transparent rank-level replication as a PMPI-layer interposer, with two consistency protocols (*mirror*: duplicate sends, higher bandwidth cost; *parallel*: coordinated senders, higher message-rate cost), and needs special handling for nondeterminism — `MPI_ANY_SOURCE` requires the leader to ship envelope information to the replica to preserve identical message ordering [rMPI11]. The tradeoff is stark and worth quoting in a design paper: replication costs ≥ 2× the resources unconditionally; checkpointing costs δ periodically plus rework on failure. Replication wins when M is small relative to δ.

### 3.7 Failure detection: heartbeats, detector classes, FLP

**FLP** (Fischer, Lynch, Paterson 1985): in a fully asynchronous message-passing system, "every protocol for this problem has the possibility of nontermination, even with only one faulty process" [FLP85]. The root cause is precisely the one that matters for agents: you cannot distinguish a crashed process from a slow one. Consensus *is* solvable synchronously; FLP rules out deterministic protocols that guarantee agreement, validity, *and* termination in the asynchronous model.

**Chandra & Toueg** [Chandra96] sidestep FLP by augmenting the system with an unreliable *failure detector* — a per-process module that continuously outputs a suspect list which need not be correct. Detectors are classified by two **completeness** properties (strong: every faulty process is eventually permanently suspected by every correct process; weak: by *some* correct process) crossed with four **accuracy** properties (strong: no correct process is ever suspected; weak: some correct process is never suspected; plus the two "eventually" variants) — eight classes. Weak completeness can simulate strong completeness, so the four strongly-complete classes are the interesting ones: **P** (perfect: strongly complete + strongly accurate — easy in synchronous systems), **S** (strong: strongly complete + weakly accurate), **◇P** (eventually perfect), **◇S** (eventually strong). Consensus with **P** or **S** tolerates any number of failures; with **◇S** or **◇P** it requires a majority of correct processes, and that requirement is *necessary* [Chandra96]. The companion result: **◇W₀** is the *weakest* failure detector sufficient to solve consensus with a correct majority [Chandra92].

**How HPC sidesteps FLP.** Three escape hatches exist in general — partial synchrony (timeouts), randomization, and failure-detector oracles [FLP-tour]. HPC takes the first, aggressively: dedicated low-jitter interconnects and a *reliable out-of-band control plane* (the runtime/RAS/resource-manager hierarchy). ULFM's failure detection is implementation-provided rather than application-provided, and EReinit's explicit design move is to put detection in the resource manager's node processes as local monitors "in contrast to consensus-based failure detection" [EReinit19]. In other words: HPC does not solve consensus in the asynchronous model; it buys a near-perfect detector from the platform and then runs a cheap agreement over it. `MPIX_Comm_agree` is the agreement layer that assumes such a detector exists.

### 3.8 Silent data corruption is a different problem — and the one that matters here

SDCs are "silent by definition and raise no warnings to users and application developers that a calculation has been corrupted" [Rezaei16]. Two facts to carry forward. (1) Most hardware faults are *not* silent: studies show "a majority of SDCs leads to noticeable impacts such as crashes and hangs but ... only a small fraction of them" produce plausible-but-wrong output — yet that small fraction is the dangerous one [Snir14]. (2) Checkpoint/restart is structurally incapable of covering SDC: "while most HPC applications use checkpoint/restart to recover from detectable failures, this technique cannot cover undetectable, silent corruptions" [Rezaei16]. Worse, an SDC can be *checkpointed*, poisoning every recovery line after it.

Detection strategies, in increasing specificity:
- **Replication + comparison.** "A classic way to detect a large proportion of SDCs (but not all) is replicating executions and comparing results" [Snir14]. RedMPI is the reference implementation: a PMPI-layer library that transparently detects corrupt messages with dual redundancy and, with triple redundancy, *votes out* the faulted process's messages and substitutes corrected results. Overheads 13%–62% depending on redundancy level and communication pattern (13%–45% dual, 20%–60% triple), and roughly invariant in process count [Fiala12].
- **Layer-relative definitions.** Rezaei et al.'s central argument is that SDC must be discussed *per system layer*, and that "application specific correctness checks can tolerate about 50% of the errors that appear in the application output" [Rezaei16] — corruption that a lower layer would flag may be harmless at the application layer, and vice versa.
- **ABFT / invariant checks.** Detect via a maintained algebraic property rather than by comparison [Huang84].
- **Approximate detection.** Because some numerical divergence is legitimate roundoff, SDC detection has moved toward techniques that use fewer resources and relax precision [Snir14].
- **The honest caveat.** "Significant uncertainty remains about the likely frequency of SDC in future systems," and exascale "is highly unlikely to be viable without error detection" [Snir14].

For the AgentMPI paper this is the single most transferable section: **an LLM agent's characteristic failure is not fail-stop, it is SDC** — the agent returns, on time, with well-formed, plausible, wrong output. Everything MPI's FT machinery does (detect a stopped process, revoke, shrink, respawn, roll back) addresses the failure mode agents exhibit *least*. And the SDC literature's conclusions — that detection requires either redundancy-plus-comparison (expensive, 13–62% in RedMPI's measured case), or a maintained invariant (ABFT-style, needs domain structure), or layer-relative correctness predicates (≈50% coverage in Rezaei's study) — map onto ensembling/self-consistency, verifier/checker agents and typed contracts, and per-layer acceptance tests respectively.

## 4. Dynamic process management (MPI-2)

**Primitives.** `MPI_Comm_spawn(command, argv, maxprocs, info, root, comm, &intercomm, array_of_errcodes)` — collective over `comm`; starts `maxprocs` new processes and returns an **inter**communicator joining `comm`'s group to the new processes' own (disjoint) `MPI_COMM_WORLD` [MPI21runtime; Huber24]. `MPI_Comm_spawn_multiple` does the same for a heterogeneous set of binaries/argv in one collective call (important because one call gives *one* new `MPI_COMM_WORLD`). Children reach their parents via `MPI_Comm_get_parent`. For joining independently-started jobs: `MPI_Open_port(info, port_name)` / `MPI_Close_port`, `MPI_Comm_accept(port_name, info, root, comm, &newcomm)` and `MPI_Comm_connect(...)` (a client/server rendezvous, optionally brokered by `MPI_Publish_name`/`MPI_Lookup_name`), `MPI_Comm_join(fd, &intercomm)` (bootstrap from an already-connected socket), and `MPI_Comm_disconnect`. `MPI_UNIVERSE_SIZE` on `MPI_COMM_WORLD` reports how many processes can usefully be started in total [MPI21runtime].

**Intercommunicators vs. intracommunicators.** An intracommunicator has one group; ranks name peers within it, and collectives span it. An intercommunicator has two disjoint groups (local and remote); a rank in a send/recv names a rank in the *remote* group; there is no intra-group communication on it. `MPI_Intercomm_merge(intercomm, high, &newintracomm)` flattens the two groups into a single intracommunicator, with the boolean `high` deciding which group gets the upper rank range. This is the standard post-spawn move: spawn → merge → treat as one team. (ULFM's `shrink` and the group-collective communicator-creation algorithm both build intercommunicators and merge them pairwise; see §6.)

**Why it is barely used.** Three independent lines of evidence:

1. **The standard itself flags the mismatch.** MPI-2's "Runtime Environment" section: "Batch queueing systems generally allocate resources before an application begins, enforce limits on resource use (CPU time, memory use, etc.), and do **not allow a change in resource allocation after a job begins**. Moreover, many MPPs have special limitations or extensions, such as a limit on the number of processes that may run on one processor" [MPI21runtime].
2. **Design-level defects.** Huber et al. enumerate: `MPI_Comm_spawn` is *blocking*, so processes cannot proceed while launch happens; processes created by one spawn share an `MPI_COMM_WORLD` and therefore cannot be individually removed (`MPI_Comm_disconnect` works across `COMM_WORLD`s, not within one), so the removal granularity is the whole spawned batch, and working around it by spawning one process at a time is prohibitively slow; and — the killer — "the specification of MPI DPM 2.0 does not describe the interaction with resource management software to change the current allocation. Most implementations therefore default to spawning new processes inside of the current allocation, potentially oversubscribing resources." Their conclusion: "approaches based on `MPI_Comm_spawn` fall short of the performance and flexibility expected of a dynamic resource approach for HPC" [Huber24] `[UNVERIFIED: full author list]`.
3. **Field evidence.** The malleability survey states plainly that dynamic process creation has existed since MPI-2 "however, most RMS operate in ways that make it difficult to add dynamic processes support, which prevents its usage in production systems. For this reason, jobs run with a fixed number of processes and may use load balancing techniques that do not rely on spawning processes" [MalleabilitySurvey]. And it fails in the mundane way you would expect: a documented Slurm case where `MPI_Comm_spawn` works under `salloc` and hangs under `sbatch` [SlurmSpawn]. Modern work routes around `spawn` entirely — DynRes uses MPI Sessions + PMIx to negotiate allocation changes with the resource manager [Huber24; MediaTUM].

The lesson for a transplant: the primitive was fine; the *resource-negotiation protocol underneath it* was left unspecified, and that omission killed it.

## 5. MPI Sessions (MPI-4)

**The problem.** The standard's own enumeration of world-model limitations: "MPI cannot be initialized from different application components without a priori knowledge or coordination; MPI cannot be initialized more than once; and MPI cannot be reinitialized after `MPI_FINALIZE` has been called" [MPI41, §12.3]. `MPI_Init` is global, once-only, irreversible state. Two libraries that each want MPI must coordinate out of band about who initializes and who finalizes — a real problem, since a library cannot know whether it is the top of the stack. Add the scaling argument from the original paper: "Requiring all processes' rank information in MPI_COMM_WORLD is too expensive. Why keep state for communication ... that will never be used by the application (connections)? Why completely wire-up a network that doesn't need [it]?" [Holmes16].

**The model.** A process instantiates a **Session** handle, queries the runtime through it, derives a **Group** from a **process set**, and from the group derives a Communicator, Window, or File — never touching `MPI_COMM_WORLD` [MPI41, §12.3].

- `MPI_Session_init(info, errhandler, &session)`. `info` carries `thread_level` (as a *string*, e.g. `"MPI_THREAD_MULTIPLE"`, not the integer of `MPI_Init_thread`) and `mpi_memory_alloc_kinds`. "Session instantiation is intended to be a lightweight operation. An MPI process may instantiate multiple Sessions. `MPI_SESSION_INIT` is always thread safe; multiple threads within an application may invoke it concurrently" [MPI41, §12.3.1]. The `errhandler` argument covers errors *during* initialization.
- `MPI_Session_finalize(&session)` must be called for every session. It "may be synchronizing on any or all of the groups associated with communicators, windows, or files derived from the session and not disconnected, freed, or closed"; unlike `MPI_Finalize` it is *not* collective over all connected processes. If the app frees all windows/files and uses `MPI_Comm_disconnect` on all derived communicators first, an implementation "should be able to implement the semantics of `MPI_SESSION_FINALIZE` as a local procedure" [MPI41, §12.3.1].
- **Process sets** are URI-named: `"mpi://WORLD"` and `"mpi://SELF"` are mandated; others (e.g. `"mpix://UNIVERSE"`, `"hwloc://L3Cache"`) may be defined; the `mpi://` namespace is reserved to the standard. A pset caches key/value tuples reachable as an `MPI_Info`, with `mpi_size` mandatory. How psets are defined and how resources map to them is implementation-dependent [MPI41, §12.3.2].
- Discovery: `MPI_Session_get_num_psets` / `MPI_Session_get_nth_pset` (names bounded by `MPI_MAX_PSET_NAME_LEN` ≥ 63) / `MPI_Session_get_pset_info`.
- `MPI_Group_from_session_pset(session, pset_name, &newgroup)` — a **local** operation; returns `MPI_GROUP_NULL` for an unknown name. Then `MPI_Comm_create_from_group(group, stringtag, info, errhandler, &newcomm)` or `MPI_Intercomm_create_from_groups(...)` builds a communicator **with no parent communicator** [OMPI-GroupFromPset; MPI41, §12.3].
- World and Sessions models may be used concurrently in one process, but `MPI_COMM_WORLD` and `MPI_INFO_ENV` are not valid when using only Sessions [MPI41, §12.3].

**Why libraries wanted it**: independent initialization without coordination; repeatable init/finalize within one process lifetime; per-session thread-support level (so one component's `MPI_THREAD_SINGLE` request does not constrain another's — hence the standard's advice that requesting `MPI_THREAD_SINGLE` "is generally not recommended, because this will conflict with other components of an application requesting higher levels of thread support" [MPI41, §12.3.1]); per-session error handlers; and lazy, needs-based wireup instead of eager all-to-all connection setup [Holmes16]. Note also the malleability angle: `mpi://WORLD` is *never changed* by resource additions; instead a *new* global pset appears [Streubel21] `[UNVERIFIED: student thesis, not peer-reviewed]`. Named psets are the mechanism by which the resource manager and MPI finally share a vocabulary — the thing MPI-2 dynamic process management lacked.

## 6. MPI-IO

**Views built from derived datatypes.** `MPI_File_set_view(fh, disp, etype, filetype, datarep, info)`. A **view** is "an ordered set of etypes" defined by three quantities: a byte **displacement** `disp`, an **etype** (the unit of access — any basic or derived datatype; offsets are counted in etypes and file pointers point at etype boundaries), and a **filetype** (either a single etype or a derived type built from multiple instances of the *same* etype; the extent of any hole must be a multiple of the etype's extent; typemap displacements must be nonnegative and monotonically nondecreasing). The filetype pattern is tiled from `disp` onward, exactly as `MPI_Type_contiguous(filetype, huge)` would tile it. "If a filetype has holes in it, then the data in the holes is inaccessible to the calling process." The default view is a linear byte stream (`disp`=0, etype=filetype=`MPI_BYTE`) [MPI41, §14.1; MPI31, §13.3]. `set_view` is collective; `datarep` and the etype's extent must be identical across the group; `disp`, `filetype`, `info` may differ — that's the whole point, since differing filetypes are how a file gets partitioned. It also **resets both individual and shared file pointers to zero**. Using shared-file-pointer routines requires identical `disp` and `filetype` too [MPI41, §14.1; OMPI-SetView]. This is the same derived-datatype machinery as message passing, reused as a *file layout descriptor* — arguably MPI's most elegant abstraction reuse [Thakur98].

**Independent vs. collective access.** Three positioning families × two synchrony families × two coordination families: explicit offset (`MPI_File_read_at`), individual file pointer (`MPI_File_read`), shared file pointer (`MPI_File_read_shared`); blocking/nonblocking; and independent vs. collective (`_all` suffix, or `_ordered` for shared-pointer collectives). `MPI_File_write_ordered` writes at the position the shared pointer would hold after all lower-ranked processes had written, i.e. rank order [OMPI-WriteOrdered].

**The two implementation techniques that justify the interface.** Because MPI-IO lets a process express a noncontiguous access in *one* call, the implementation gets optimization latitude that POSIX denies it [Thakur99].
- **Data sieving** (single-process, noncontiguous): instead of one I/O call per contiguous piece, read one large block spanning all the pieces — including the unwanted "holes" — and extract locally. One I/O call, at the cost of transferring extra bytes. Writes need read-modify-write and therefore file locking, which is why ROMIO falls back to POSIX I/O on file systems without locks (e.g., PVFS). ROMIO hints: `ind_rd_buffer_size`, `ind_wr_buffer_size`, `romio_ds_read`, `romio_ds_write` [Thakur99; ROMIOguide; ChiCho03].
- **Two-phase collective I/O** (a.k.a. collective buffering), originally del Rosario, Bordawekar & Choudhary [delRosario93]: decouple the data distribution *on compute nodes* from the distribution *in storage*. Partition the aggregate accessed file region into **file domains** assigned to a subset of **aggregator** processes; for reads, aggregators do large contiguous reads (internally via data sieving) and then redistribute; for writes, data is gathered from processes and then written. ROMIO hints: `cb_config_list`, `cb_nodes`, `cb_buffer_size`, `romio_cb_read`, `romio_cb_write` [Thakur99; ROMIOguide].

**The consistency model, precisely.** MPI defines **three** levels [MPI41, §14.6.1]:
1. sequential consistency among all accesses using a *single file handle*;
2. sequential consistency among all accesses using file handles from a *single collective open*, **with atomic mode enabled**;
3. **user-imposed** consistency for everything else.

"Sequential consistency means the behavior of a set of operations will be as if the operations were performed in some serial order consistent with program order; each access appears atomic, although the exact ordering of accesses is unspecified" [MPI41, §14.6.1]. Case analysis:
- Same handle `fh1`: sequentially consistent if atomic mode is set. In **nonatomic mode** (the default in the standard), operations are sequentially consistent only if they are "either nonconcurrent, nonconflicting, or both." Two accesses *conflict* if they overlap and at least one is a write.
- Handles from the same collective open: as above.
- Handles from **distinct collective opens**: `MPI_File_sync` is required for sequential consistency; opening and closing a file each perform an implicit sync.

`MPI_File_set_atomicity(fh, flag)` is collective over the handle set from one open; all processes must pass identical `fh` and `flag` [MPI41, §14.6.1]. Note the portability trap: Open MPI's *default* is `true` for multi-node jobs and `false` on a single SMP [OMPI-SetAtomicity], i.e. the default differs from the standard's default and across configurations.

`MPI_File_sync(fh)`: "causes all previous writes to `fh` by the calling process to be transferred to the storage device. If other processes have made updates to the storage device, then all such updates become visible to subsequent reads of `fh` by the calling process." It is **collective**; the user must ensure all nonblocking requests on `fh` are complete first, or the call is erroneous; and it "is not guaranteed to be a temporally synchronizing function" [MPI41, §14.6.1; OMPI-FileSync]. Hence the canonical portable idiom is **sync–barrier–sync**, which guarantees conflicting accesses are not *concurrent* rather than making them atomic. Two costs, both noted in an active Forum proposal: sync forces a flush all the way to the storage device even when you only wanted visibility, and "requires synchronization among all processes that collectively opened the file, regardless of whether they participate in the current I/O phase," which "prevents optimizations that distinguish between 'producers' and 'consumers'" — motivating proposed non-collective `MPI_File_flush`/`MPI_File_refresh` and a *flush–barrier–refresh* model [MPIIssue995]. In practice most MPI-IO applications avoid all of this by partitioning the file into disjoint per-process regions so that no accesses conflict and nonatomic mode is safe [Klockwood].

## 7. Communicator management

**Context IDs as distributed agreement.** A communicator is a group plus a *communication context* — a tag-space separator guaranteeing that messages on one communicator can never match receives on another. Allocating a context ID is inherently an agreement problem: every participant must pick the *same* previously-unused ID. Implementations typically maintain a local bit-vector of free IDs and run an `MPI_Allreduce` with bitwise AND to find an ID free everywhere [Dinan12; ICLctxid16]. Two consequences: (i) communicator creation costs a collective, which is why `MPI_Comm_dup` is not free; (ii) making it thread-safe is genuinely hard — Dinan et al. extended MPICH2's multithreaded allocator and "discovered a bug in the production algorithm that can result in deadlock," fixed it, and proved the corrected algorithm deadlock-free [Dinan12].

**`MPI_Comm_dup` and `MPI_Comm_idup`.** `dup` copies the group and topology, replicates cached attributes via the copy callbacks, and allocates a *fresh* context — the standard mechanism by which a library obtains a private communication space so its messages cannot be intercepted by user code. `MPI_Comm_idup(comm, &newcomm, &request)` is the nonblocking variant: "With the exception of its nonblocking behavior, the semantics of `MPI_COMM_IDUP` are as if `MPI_COMM_DUP` was executed at the time that `MPI_COMM_IDUP` is called. For example, attributes changed after `MPI_COMM_IDUP` will not be copied to the new communicator" [MPI41/MPI50, §7.4.2]. It is erroneous to use `newcomm` before the request completes. Why it was needed: a library that must dup a communicator during *its own* nonblocking initialization otherwise has to execute a blocking collective inside a nonblocking API, which either serializes or deadlocks against other libraries doing the same. `idup` lets communicator setup be pipelined and overlapped like any other nonblocking collective.

**`MPI_Comm_split`, `MPI_Comm_split_type`.** `split(comm, color, key, &newcomm)` is collective over `comm` and partitions it: one new communicator per distinct color, ranks ordered by key then by old rank; `MPI_UNDEFINED` as color yields `MPI_COMM_NULL`. Colors and keys are supplied *distributively* — each process states only its own intent — which makes split the natural tool for data-driven regrouping. `split_type(comm, split_type, key, info, &newcomm)` splits by an implementation-known *property* rather than a user color; `MPI_COMM_TYPE_SHARED` groups processes that can create a shared-memory region, which is precisely the input to `MPI_Win_allocate_shared`. Hardware-topology types (`MPI_COMM_TYPE_HW_GUIDED`/`_HW_UNGUIDED`) were added later.

**`MPI_Comm_create_group` and why it beats `MPI_Comm_create`.** `MPI_Comm_create(comm, group, &newcomm)` must be called by **all** processes in `comm`, even those not in `group`. `MPI_Comm_create_group(comm, group, tag, &newcomm)` "must be called by all MPI processes in `group`, which is a subgroup of the group of `comm`," requires `comm` to be an intracommunicator, propagates no cached information and no topology, and is a *local no-op* returning `MPI_COMM_NULL` for a caller passing `MPI_GROUP_EMPTY` [MPI41/MPI50, §7.4.2]. The `tag` argument distinguishes concurrent calls, including from multiple threads. Three motivations, from the proposal and follow-on work: **fault tolerance** — "when a node failure occurs, processes must create a new communicator to re-establish collective communication; however, traditional communicator creation would require participation from failed processes"; **load balancing** — asynchronously reassigning idle processes to loaded teams; and **cost** — when the target group is much smaller than the parent, participation by the whole parent is pure waste [Dinan12; Dinan11; ICLctxid16]. Dinan et al.'s pre-standard user-level emulation of it needed log|group| intercommunicator-create-plus-merge rounds; the native implementation eliminates those O(log n) communicator creations, and group-collective creation is several times faster than collective creation when the output group is smaller than the parent [Dinan11; Dinan12].

**Info objects and attribute caching.** `MPI_Info` is an opaque (key, value) string map used pervasively as the *hint* channel: window creation (`accumulate_ordering`, `accumulate_ops`, `same_size`, `no_locks`), file open (`cb_nodes`, `cb_buffer_size`, `romio_ds_write`, …), spawn (`host`, `wdir`), session init (`thread_level`), and MPI-4 assertions (`mpi_assert_no_any_tag`, etc.). The design invariant: hints never change semantics, only performance — an implementation may ignore any of them. **Attribute caching** (`MPI_Comm_create_keyval` with copy and delete callbacks, `MPI_Comm_set_attr`/`get_attr`, and the analogous window and file variants) lets a library attach private state to a communicator and have it propagate on `dup` (copy callback) and be reclaimed on free (delete callback). This is how a library keeps per-communicator state without a side table keyed by handle — and the reason `MPI_Comm_free` semantics matter: "if attributes are cached on such an opaque object, then the delete callback functions are only invoked when the object is explicitly freed (or disconnected)" [MPI41, §12.3.1].

## 8. Threads

**The four levels** (requested via `MPI_Init_thread(&argc, &argv, required, &provided)`, or per-session via the `thread_level` info key):
- `MPI_THREAD_SINGLE` — one thread of execution, period.
- `MPI_THREAD_FUNNELED` — multiple threads, but only the thread that called `MPI_Init_thread` may call MPI.
- `MPI_THREAD_SERIALIZED` — any thread may call MPI, but calls must not be concurrent (the app serializes them).
- `MPI_THREAD_MULTIPLE` — any thread may call MPI at any time; the library is fully thread-safe.

`provided` may be lower than `required`; portable code must check. Note the Sessions-model advice that requesting `MPI_THREAD_SINGLE` is discouraged precisely because it conflicts with other components requesting more [MPI41, §12.3.1].

**Why `MPI_Mprobe`/`MPI_Improbe` were added.** `MPI_Probe`/`MPI_Iprobe` *find* a message but do not *match* it, and "since the list of incoming messages is global among the threads of each MPI process, it can be hard to use this functionality in threaded environments" [MPI41/MPI31, §3.8.2]. The concrete race: thread A probes, learns the size, allocates a buffer, calls `MPI_Recv` — and thread B's intervening receive takes the message, so A's receive gets a *different* message into a wrongly-sized buffer. The matched probe fixes this by *matching at probe time*: `MPI_Improbe(source, tag, comm, &flag, &message, &status)` returns a **message handle** to the matched message; "Unlike `MPI_IPROBE`, no other probe or receive operation may match the message returned by `MPI_IMPROBE`. Each message handle returned by `MPI_IMPROBE` must be received with either `MPI_MRECV` or `MPI_IMRECV`" [MPI41, §3.8.2]. `MPI_Mprobe` is the blocking form. Progress is guaranteed except when another concurrent matching probe or receive at the same process takes the message [Gregor12]. The original proposal went so far as to propose deprecating `MPI_Probe`/`MPI_Iprobe`; the Forum kept them [Gregor12].

**Endpoints: proposed, prototyped, abandoned.** `MPI_Comm_create_endpoints` would have let one OS process host *multiple ranks*, so threads could be addressed as first-class MPI processes and be mapped to separate network contexts, command queues, and matching structures [Dinan13; EPticket380]. It was not standardized. The reasons, from the people who killed it: it "enforce[s] the new concept of endpoints upon users through new APIs and put[s] the onus of mapping threads to the endpoints on the domain scientist, potentially hurting productivity"; prior demonstrations did not compare fairly against an MPI-3.1 implementation using multiple hardware contexts, and did not expose the equivalent parallelism to the MPI-3.1 baseline; and progress-semantics corner cases were ignored [Zambre20]. The MPICH team's blunter framing: "A key flaw in the endpoint proposal ... is the inflation of thread context into virtual processes. To a multithread programmer, a process and a thread are separate concepts. ... With the endpoints proposal, the process become[s] less identifiable. Users may have to manage their own endpoint ranks to process the rank translation table. The endpoints proposal also makes interthread messages equally accessible as interprocess messages. Since users rarely need interthread messages, this inflation makes MPI more difficult to understand and use" [MPICH3591]. The winning alternative was **implicit Virtual Communication Interfaces**: the implementation infers communication parallelism from *existing* MPI-3.1 structure (distinct communicators, distinct windows, tags) and maps it onto internal VCIs, "in the majority of cases ... achiev[ing] communication performance equal to the performance of user-visible endpoints and MPI everywhere without sacrificing correctness" [Zambre20]. The Forum "is no longer pursuing the endpoints proposal"; MPICH is pursuing `MPIX_Stream` instead [MPICH3591].

**MPI+OpenMP hybrid issues** (summarizing the above rather than a dedicated source): a single `MPI_THREAD_MULTIPLE` rank per node must funnel all threads' traffic through one set of network resources, so per-thread throughput collapses under lock contention and shared matching queues — the problem endpoints and VCIs both attack. The universal workaround is *one communicator per thread*, which sidesteps MPI's message-ordering constraints and is exactly the parallelism VCIs exploit [Zambre20]. `MPI_THREAD_MULTIPLE` also historically carried a large fixed cost, pushing many codes to FUNNELED with hand-rolled aggregation.

## 9. Transfer notes for an LLM-agent setting

The value of MPI here is not the API but the *taxonomy of promises*. Below, for each mechanism, the sharpest analogue and a skeptical verdict.

**RMA windows → the scoped blackboard. Transfers well, and the isolation is the prize.** The window's two isolation properties are exactly what a shared agent scratchpad needs and what "one big JSON blob everyone can write" lacks: (i) only agents in the window's group can touch this region, (ii) an agent's memory is unreachable unless explicitly *attached*. An AgentMPI window is a named, group-scoped region of a blackboard, and the four creation variants map cleanly: `Win_create` = expose an existing artifact (a file, a buffer) into a group; `Win_allocate` = have the harness allocate the region so it can be addressed uniformly across agents (symmetric naming — the harness assigns stable keys instead of per-agent offsets); `Win_create_dynamic` = a scratchpad whose key set grows at runtime (the normal case for agents, and worth noting that MPI marks this variant as *more* expensive, which is honest — dynamic key spaces cost metadata); `Win_allocate_shared` = co-located agents sharing a process address space or a filesystem, allowed to read/write directly rather than through the protocol. Keep the `MPI_WIN_MODEL` attribute idea: a window should *advertise* whether reads see writes without an explicit sync.

**Put/Get vs. accumulate/CAS → transfers, but re-derive the granularity.** MPI's honesty about `MPI_Put` — concurrent puts to a location have *undefined* result, and the target may end up with bytes from several — is the right stance for an agent blackboard doing blind overwrite, and it should be stated that plainly rather than papered over. The atomics are the interesting import: `Fetch_and_op` and `Compare_and_swap` are exactly the primitives needed for a lock-free work queue or a claim-a-task protocol among agents, and they are cheap because they are single-element. The transferable design rule is MPI's own: *element-wise* atomicity, with concurrent accumulates to the same element serialized in some order, and overlapping updates of *different* sizes at *different* displacements explicitly undefined. In an agent harness the "element" is a blackboard key or a JSON path — so an append-to-list or increment-counter operation can be atomic while a whole-document merge cannot. **Do not transfer** MPI's default *strict* accumulate ordering (rar/raw/war/waw) uncritically: it orders only same-origin/same-target pairs, which for agents means "one agent's own writes to one key are applied in the order it issued them" — probably worth guaranteeing, and probably cheap, but say so explicitly rather than inheriting the four-flag `accumulate_ordering` vocabulary, which is hardware-motivated.

**Epochs → transfers, but as *sessions of intent*, not as memory fences.** The access/exposure asymmetry is a genuinely good idea for agents: an access epoch is "I am now going to read/write this shared region, and here is when I'm done"; an exposure epoch is "my region is open for others to touch during this interval." The one-to-one matching between them is what lets a harness know that a reader saw a consistent snapshot. **Be skeptical about fence.** `MPI_Win_fence` is a collective barrier over the whole window group — in an agent setting that means every agent stalls at the slowest one, which is catastrophic when latencies are seconds-to-minutes and heavy-tailed, not microseconds. PSCW (post/start/complete/wait, with explicit *groups*) transfers much better: it is pairwise, it names its counterparties, and MPI's own rationale for it — "more efficient when each MPI process communicates with few (logical) neighbors" — is exactly the agent regime. Also import MPI's *weak synchronization* license: `start` may return before the target exposes. An agent should be able to declare intent to write without blocking on the reader being ready.

**Locks → transfers with one substitution: exclusive/shared, but not window-granularity.** The shared/exclusive distinction is correct and cheap to explain: read-only or accumulate-only agents take shared, mutating agents take exclusive. `Lock_all` is the right default posture for a long-lived blackboard — one shared epoch held for the agent's lifetime, with `flush` when you need someone else to see your write. The `flush` vs. `flush_local` split is the single most transferable detail in the whole RMA chapter: "my write is durably visible to others" and "I can reuse my buffer / my turn is done" are different questions with different costs, and every agent harness conflates them. **Do not transfer** window-granularity locking. MPI locks the whole window because byte-range locks are expensive in hardware; a harness has no such excuse, and per-key or per-path locks are the obvious right granularity. Also **do not transfer** the erroneousness of mixing locks and exposure epochs — MPI made that erroneous to avoid a runtime cost it did not want to pay; a harness should just make it work.

**Separate vs. unified memory model → mostly does *not* transfer; keep the query, drop the model.** The distinction exists because some hardware is non-cache-coherent. There is no agent analogue of a non-coherent cache. What *does* transfer is the shape of the problem — an agent's local belief state versus the shared blackboard is genuinely a private-copy/public-copy pair, and `MPI_Win_sync` is genuinely "reconcile my local view with the shared one." So keep the *attribute* (`WIN_MODEL`-style: does this window guarantee read-your-writes and eventual visibility, or must you sync?), because backends will differ (in-process dict = unified; S3 with eventual consistency = separate). Also import the warning that *process* synchronization is not *memory* synchronization: an agent handoff message ("I'm done, your turn") does not by itself guarantee the recipient sees the writes, if the store went through a caching layer. MPI's barrier-then-stale-read examples are directly reusable as cautionary tales.

**ULFM revoke/shrink/agree → the most valuable import, and `revoke` is the crown jewel.** All three have exact agent analogues:
- **`revoke`** solves *the* multi-agent liveness bug. Non-uniform failure notification is worse for agents than for MPI: agent A discovers the orchestrator's plan is void (a subagent died, a budget blew, a tool is down) while agents B, C, D sit blocked waiting for messages A will now never send. MPI's exact scenario. `revoke` is the primitive that says: *one* participant can unilaterally poison a communication scope so that every pending and future operation on it fails fast, letting everyone branch to recovery — without aborting anyone. Note the two properties to preserve: it is **not collective** (one caller suffices — critical, since in an agent system usually exactly one participant knows), and it needs **reliable propagation** despite the failure (the harness must broadcast the revocation over an overlay that survives the dead node, which for agents means the control plane, not the agent-to-agent channel). Also preserve the *lack* of ordering: a receive may fail with `REVOKED` even though the matching send was issued first. Agent harnesses today mostly implement "cancel the whole run"; `revoke` is the scoped version, and scoping is what makes partial recovery possible.
- **`shrink`** = reconstitute the team without the dead agent, with the roles/indices compacted. The important semantic details all transfer: it must be collective *even on a revoked scope* (otherwise you cannot recover), it must never itself fail with REVOKED/PROC_FAILED, its result is "a split that succeeds despite failures," and it is **best-effort** — the new team may still contain an agent that turns out to be dead. That last caveat is the one harness authors forget.
- **`agree`** = fault-tolerant agreement on a boolean, with *uniform* reporting. Its canonical MPI uses translate one-for-one: did this round succeed everywhere? is it safe to commit this checkpoint/artifact? do we all agree who is dead? The `ack_failed` + `agree`-until-SUCCESS loop is directly the algorithm for "get a globally consistent view of which agents are gone." **But import the cost warning too**: agree is more expensive than a plain reduction and must be used parsimoniously. For agents, whose per-message cost is already enormous, that argues for agreeing on *epoch boundaries* only, not per operation.
- **Be skeptical** of ULFM's overall track record. Laguna et al. found it delivered "few benefits for more common bulk synchronous MPI applications" and that a much simpler primitive — Reinit's global, backward, non-shrinking rollback — fit the dominant workload better [Laguna16]. The lesson transfers: if the dominant multi-agent pattern is "orchestrator fans out, gathers, retries," then a `restart_from_last_good_state` primitive may beat a general revoke/shrink/agree API, and the paper should argue for one rather than assume generality is free. Also note that ULFM has been in draft for over a decade and is *still* not in MPI-5.0 — a cautionary data point about proposing a fault-tolerance layer for a mature ecosystem.

**Fail-stop machinery in general → largely does *not* transfer; SDC does.** This is the sharpest negative result in this memo. Every mechanism above assumes **fail-stop**: an agent either works or is detectably gone. LLM agents' characteristic failure is the opposite — they return on time, well-formed, confident, and wrong. That is silent data corruption, and the SDC literature says three things that transfer directly. (1) Checkpoint/restart is structurally useless against it, and worse, a corrupt state gets checkpointed and poisons every subsequent recovery line — the agent-memory analogue is a wrong intermediate conclusion that gets written to the shared scratchpad and cited by every downstream agent thereafter. (2) The detection strategies are redundancy-plus-comparison (RedMPI: dual redundancy detects, triple redundancy *votes*, at 13–62% overhead [Fiala12]) — i.e., self-consistency sampling and majority voting, with the *same* honest accounting of cost; a maintained invariant (ABFT: the checksum survives the transformation, so its violation localizes the error [Huang84]) — i.e., typed outputs, schema validation, unit tests, executable checks, anything that is preserved by a correct step and broken by a wrong one; and layer-relative correctness predicates (Rezaei et al.: application-specific checks tolerated ~50% of output errors [Rezaei16]) — i.e., per-stage acceptance tests, with the corollary that "correct" must be defined per layer, since a hallucinated intermediate that does not affect the final answer is not a failure at the top layer. (3) The frequency is *not well characterized* [Snir14] — the analogous honesty for agents is that per-step error rates are workload-dependent and mostly unmeasured.
Second-order transfer: **`agree` is the right shape for SDC too.** It is already a *validation* primitive ("did this round succeed everywhere?"), and generalizing its flag from a boolean to a content digest turns it into distributed cross-checking. That is a genuinely novel-looking move for the paper.

**Failure detection → the FLP escape hatch transfers, and agents make it harder.** FLP is directly binding: you cannot distinguish a crashed agent from one that is slow, and LLM latencies are heavy-tailed enough that this is a live operational problem, not a theoretical one. Chandra–Toueg's completeness/accuracy lattice is the right vocabulary for a harness's timeout policy: aggressive timeouts buy strong *completeness* (dead agents get suspected) at the cost of *accuracy* (live-but-slow agents get killed), which is exactly the tuning knob every agent framework has and none names. HPC's escape hatch transfers too: buy a near-perfect detector from a layer *below* the agents. For an agent harness that means the process supervisor / container runtime / API-level request state, not agent-to-agent heartbeats. Adopt MPI's honesty here: "MPI makes no assumption about asynchronous progress of the failure detection" and "it is possible that only the calling MPI process has detected the reported failure" [ULFMdraft22]. Failure knowledge in an agent system is *local by default*, and `agree` is how it becomes global.

**Spawn → transfers, but the *lesson* is the negative one.** `MPI_Comm_spawn` is the obvious model for spawning subagents, and the intercommunicator/intracommunicator distinction is genuinely useful: a spawned subagent team should start in a *two-group* relationship (parent group ↔ child group, with cross-group addressing only) and `Intercomm_merge` into one team only when you deliberately want a flat peer structure. But the honest finding is that MPI's dynamic process management is *the least-used part of MPI*, for reasons that apply verbatim: `spawn` is **blocking** (the parent stalls while children launch — unacceptable when launch means loading a model or booting a sandbox); the **removal granularity** is the whole spawned batch, since processes sharing a `COMM_WORLD` cannot be individually disconnected, and spawning one at a time to work around it is prohibitively slow; and the fatal one, **the interaction with the resource manager was left unspecified**, so implementations spawn inside the existing allocation and oversubscribe [Huber24; MalleabilitySurvey]. For agents, "the resource manager" is the token/cost budget, the rate limiter, and the concurrency pool. An AgentMPI spawn that does not specify how a subagent's budget is carved out of the parent's will reproduce MPI's exact failure — the primitive will work in demos and be unusable in production. Make spawn nonblocking, make individual subagent teardown a first-class operation, and specify the budget-negotiation protocol.

**Sessions → transfers almost unchanged, and is underrated.** The world-model problems are the agent-framework problems today: you cannot initialize the harness from two independent components without out-of-band coordination; you cannot initialize twice; you cannot re-initialize after shutdown. Any harness that is also a *library* — imported by another harness — hits all three. The Sessions answer transfers wholesale: a lightweight, **thread-safe, multiply-instantiable** session handle; discovery of *named process sets* through the session; groups derived locally from psets; communicators/windows derived from groups **with no parent communicator**. Import three specifics. (1) **URI-named psets with a reserved namespace** (`mpi://WORLD`, `mpi://SELF`, plus implementation namespaces) is exactly the right shape for agent-set naming (`agent://ALL`, `agent://SELF`, `agent://role/reviewer`, `provider://anthropic`), and psets carrying an info map with a mandatory size key is a nice touch. (2) **Per-session error handler supplied at init**, covering failures *during* initialization — agent harnesses routinely have no way to handle a failure in their own startup. (3) **Per-session thread/concurrency level**, with the standard's own warning that requesting the most restrictive level is antisocial because it constrains other components. Also note the malleability property: `mpi://WORLD` is immutable, and resource changes produce a *new* pset rather than mutating the old one [Streubel21] — immutable named sets plus new sets on change is a much better fit for a dynamic agent population than a mutable global roster. Finally, note that psets are the vocabulary MPI-2 dynamic process management was *missing*: it is the same fix.

**MPI-IO consistency → transfers directly to concurrent repo/file edits, and this is the most immediately practical import.** Multiple agents editing one repository is precisely "multiple processes accessing one file," and MPI's three-level model is a better vocabulary than anything agent frameworks currently use. Map it: *same file handle* = one agent's own edits (always sees its own writes); *handles from one collective open* = a coordinated agent team that agreed on the file layout up front; *handles from distinct opens* = uncoordinated agents, where you must impose consistency yourself. Import the exact definitions of **conflicting** (overlapping and at least one write) and **concurrent**, and the guarantee that nonatomic mode is safe when accesses are "either nonconcurrent, nonconflicting, or both." Then import the practitioner's conclusion: real MPI-IO applications mostly avoid the whole problem by giving each process a *disjoint* region [Klockwood] — the agent analogue is assigning disjoint files or disjoint code regions per agent, which is the correct default and should be the harness's recommended pattern. Import **atomic mode** as an opt-in expensive mode for genuinely conflicting edits, and **sync–barrier–sync** as the portable idiom for making a producer's writes visible to a consumer. And import the Forum's live *criticism* of `File_sync`: it forces a flush to durable storage when you only wanted visibility, and it is collective over everyone who opened the file "regardless of whether they participate in the current I/O phase," which "prevents optimizations that distinguish between 'producers' and 'consumers'" [MPIIssue995]. An agent harness should split these from the start: `publish` (make my edits visible) and `refresh` (pick up others' edits), non-collective, rather than one collective `sync`. **File views are the wildcard**: a filetype is a *sparse, tiled, holes-allowed* description of which parts of a file a participant may touch, with the guarantee that data in the holes is inaccessible. That is a remarkably precise formalization of "agent X may only edit these regions of this file," and it is buildable from composable descriptors. That may be the least obvious and most useful thing in this memo.

**Thread levels → transfers as a concurrency-contract vocabulary.** SINGLE/FUNNELED/SERIALIZED/MULTIPLE is a good four-point scale for "how may this agent (or this tool) be called concurrently?", and the `required`/`provided` negotiation — you ask, the implementation tells you what it can actually do, and portable code checks — is a pattern agent frameworks lack entirely for tools and MCP servers. FUNNELED in particular has a clean analogue: only the orchestrator may call the shared resource. The `Mprobe` lesson transfers sharply and concretely: **probe-then-receive is a race, and the fix is to match at inspection time.** Any agent harness with a shared inbox where one worker peeks at a message and another takes it has this exact bug; the fix is MPI's — return an opaque *message handle* that has already been matched and can only be consumed once, and guarantee that no other operation can match it. That is a two-line API change with real correctness content. **Be skeptical about endpoints.** The proposal — let one process host multiple addressable ranks so threads become first-class peers — is the tempting design for "let each concurrent task inside an agent be its own addressable participant," and it *failed*, for reasons that transfer: it inflated an internal concurrency mechanism into a user-visible identity ("the process becomes less identifiable. Users may have to manage their own endpoint ranks"), it made an operation users rarely want (intra-agent messaging) as prominent as one they always want (inter-agent messaging), and the winning alternative extracted the same parallelism *implicitly* from structure the user was already expressing [Zambre20; MPICH3591]. Before AgentMPI gives sub-agent threads their own ranks, it should check whether distinct scopes (per-task communicators/windows) already express the parallelism.
