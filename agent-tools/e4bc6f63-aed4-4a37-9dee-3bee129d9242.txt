# An Evaluation of High Performance Fortran

## Abstract

High Performance Fortran (HPF) is evaluated by rewriting sequential model programs for Householder reduction, simulated annealing, and grid relaxation. The author concludes that HPF has severe conceptual and practical limitations.

## INTRODUCTION

The work described here is a continuation of my previous research on model programs for parallel scientific computing [1] [2] [3] [4] . These program were originally written in the sequential programming language Pascal and were then rewritten in SuperPascal [5] and occam [6] to run on message parallel architectures. The purpose of the present work is to determine if the sequential programs can be rewritten with minimal changes in High Performance Fortran (HPF) [7] to run on data parallel architectures.

My previous studies led to the development of a collection of model programs that solve regular problems in science and engineering (Table I ). Although I chose realistic examples from computational science, my aim was not to find faster algorithms for particular applications. The primary goal was to discover new relationships between algorithms that solve different problems. Each model program is viewed as an instance of a programming paradigm--a class of programs that solve different problems, but have the same control structure. A model program has a sequential or parallel component that implements the common control structure and a sequential component for a specific application. The clear separation of the issues of parallelism and the details of application makes the parallel model programs easy to understand.

The common control structure of a programming paradigm is sometimes called an algorithmic skeleton, a generic program, or a program template. This concept has also been explored by Cole [8] , Dongarra [9] and others.

It should be possible to move model programs based on the same paradigm to different parallel architectures with reasonable effort by rewriting the common control structure. This paper describes how this hypothesis was tested by rewriting three of the sequential model programs in HPF and running them on a DEC Alpha Cluster. HPF supports data parallelism in which several processors simultaneously perform the same operations on different elements of large arrays. These arrays are distributed throughout the local memories of the processors. The experiments were planned by me and carried out by David Jakel. Initially we were familiar with message parallelism but knew nothing about HPF or Fortran 90. In each experiment we rewrote a sequential model program in Fortran 90. We then attempted to make it parallel by using as few features of HPF as possible. In our attempts to preserve the original structure of a program, we would often deliberately write incorrect HPF to illustrate the extent to which language restrictions can complicate the task of making a sequential program parallel. More often, however, we wrote incorrect programs because it remained a mystery to us how HPF programs run on parallel architectures.

A comparison of Algorithms 1 and 4 reveals a problem that occurred in every experiment with HPF. When you rewrite a well-structured sequential program in HPF, the restrictions of the language and its implementation force you to unravel the program structure. It becomes necessary to replace some subroutine calls by the subroutine bodies, rewrite inner loops in terms of array sections, and represent local variables by global, distributed vectors.

Table II shows the performance of the parallel Householder reduction when p processors solve 1500 linear equations. The run time Tp is dominated by the parallel matrix transformation of O(n3/p). The speedup Sp = T1/Tp is limited by hidden processor communication, which takes place whenever processors refer to matrix elements kept in the memories of other processors. Unfortunately, we have no documentation of when and how processor communication takes place. Since the number of processors available was small, we were unable to determine the complexity of processor communication by experiments. The details of communication hidden by the compiler (and its documentation) prevented us from formulating and testing an accurate performance model. Consequently, we gained no general insight into the performance limitations of HPF. This is in marked contrast to my previous work which predicted the performance of message parallel Householder reduction accurately within 1% [4] .

In scientific computing, performance is the only reason to prefer parallel over sequential execution. That is why a computer scientist, who studies a parallel algorithm, is looking for general insight into its parallel complexity. A parallel language and its implementation may hide the details, but not the complexity, of communication. This is a serious flaw of the HPF implementations we have used.

## PARALLEL SIMULATED ANNEALING

Simulated annealing can find a (nearly) shortest tour through n cities. Due to the probabilistic nature of the metiaod, we repeat the computation using different random numbers and select the shortest tour obtained in, say m, trials [4, 11] . This is an ideal problem for parallel computing. The set of cities can be broadcast to p processors, which then perform the trials in parallel. Since the processors do not communicate during the computation, the parallel speedup should be nearly perfect (Sp ~ p). Again, the first step was to rewrite a Pascal program [4] in Fortran 90.

Algorithm 6 computes m tours of n cities. The tours are stored in an n x rn trial matrix of cities. Each column defines a tour with a separate trial number. When the subroutine is called, each tour has already been initialized with the cities in some arbitrary order. Simulated annealing uses the trial numbers and initial tours to find different near-optimal tours. Unfortunately, HPF does not accept a procedure call in a forall statement. You might consider replacing the call by the procedure body and turn each parameter and local variable into a distributed array. However, you would then have to do the same for every procedure called indirectly by Algorithm 6. This would replace nine well-structured procedures by a single statement and require 45 distributed arrays. Fortunately, such complete destruction of the program structure is impossible, since five of the procedures use control structures which cannot occur either in a forall statement. We therefore decided not to use forall statements.

We briefly considered declaring the do statement in Algorithm 6 to be "independent". In theory, this should permit the rn subroutine calls to run in parallel. This is an insecure form of parallelism in which the prpgrammer is completely responsible for the absence of race conditions [H6.4]. However, our HPF compiler did not support this option. So we had to try something else. Now, according to the HPF Handbook, "HPF programs may call procedures written in other programming styles or other programming languages. Because such procedures are themselves outside HPF, they are called extrinsic procedurcsd' [H8]. As a special case, an extrinsic procedure may be written in a sequential subset of HPF. ## PARALLEL GRID RELAXATION

In our last experiment we computed equilibrium temperatures on a square grid with fixed boundary temperatures by using the method of successive overrelaxation (SOR) to solve Laplace's equation [3, 11] .

The grid is represented by a real matrix u which holds the n x n interior temperatures surrounded by a border of 4(n + 1) boundary temperatures. Every grid element has a parity which is either even (0) or odd (1) . Even and odd elements alternate like black and white squares on a chessboard:

0 i 011 0 i,!0 1 0 1 0

The grid is updated (or "relaxed") n times. In each relaxation step, the even elements are updated before the odd ones. Every interior temperature is replaced by a weighted sum of the four surrounding temperatures. Table IV shows the run time T(p, n) in seconds when this program uses p processors to relax an n x n grid n times. Both experiments are scaled runs, in which each processor relaxes a grid (or subgrid) of the same size (175 × 175). So, in each case, the local computation during a single relaxation step takes O(175 × 175) time. When 4 processors perform a relaxation step, each processor needs the values of a single row and a single column held by its two nearest neighbors. This should only add a communication time of 0(2 × 175) (although the overhead of transmitting single reals may be substantial on a parallel computer that is not transputer-based).

Since the problem requires n relaxation steps, and since each processor updates a grid of constant size in each step, one would expect the run time per relaxation step, T(p, n)/n to be practically constant in scaled runs. In other words, the ratio of the run times should be T(4,350)/T(1,175) = 350/175 = 2. However, due to (hidden) inefficiences of the HPF implementation, the actual ratio is almost 7.

The four processor case ran 30 % faster. The ratio of the run times is now 6 (Table V ). The lesson of this experiment is a sad one: Do not use function calls in parallel assignment statements(!) A cryptic message from the compiler probably explains the poor performance of this parallel program. Oa four processors, the forall statement creates a duplicate updated grid of 1 Mb (350 × 350 64-bit reals). The elements of this hidden grid are then assigned to the elements of the 1 Mb grid u declared in the program. Needless to say, the decision to duplicate a grid of 122,500 elements on a parallel computer that can only update four elements at a time is absurd. Although the HPF Handbook makes it clear that a parallel assignment statement must be executed like that [H6.2.2], it didn't quite hit us until we saw it in practice. The reason is quite simply that no sensible programmer would do it that way in a language with message parallelism.

The masked forall statement examines each of the n × n grid elements, but updates only half of them. To eliminate superfluous inspection, we partitioned the interior elements into four sets with priorities 0, 1, 2, and 3:

0 2 0 2 3 1 3 1 012 0 2 3 I 3 1

By updating these sets in their order of priority, we were able to replace the outer do statement on the parity bit b and the inner forall statements in Algorithm 9 by four forall statements without masks: forall (i= 1 : n-1 : 2, j --i : n-1 : 2) u(i, j) = nextstate inline as before end forall forall(i=2: n: 2, j-= 2: n: 2) u(i, j) = nextstate inline as before end forall forall(i= 1 : n-1: 2, j = 2 : n: 2) u(i, j) -~ nextstate inline as before end forall forall(i=2: n: 2, j = 1 : n-1 : 2) u(i, j) = nextstate inline as before end forall where n is even.

This clumsy unraveling of the original program structure made both the single and the four processor case 4 times faster. However, the ratio of the run times was still three times larger than it ought to be (Table VI ). The parallel computation now creates four temporary blocks of 0.25 Mb each.

Another HPF implementation for a different parallel computer turned out to be even less efficient. I will spare you the details of how the parallel performance was improved further by replacing the call of the subroutine, relax, by its body.

This concludes the sad tale of a parallel computation that potentially is among the most efficient one can imagine. In 1993, I published a message parallel program that relaxed a 1500 x 1500 grid on 36 transputers with a parallel efficiency of 0.95 [3] . In six scaled runs with 1 to 36 processors, the ratio T(p, n)/n varied by 5 % only. CONCLUSION I have evaluated High Performance Fortran (HPF) by rewriting sequential model programs for Householder reduction, simulated annealing, and grid relaxation. The experience can be summarized as follows:

1. The HPF Handbook of 300 pages [7] is neither a concise definition nor a suitable tutorial of the language. It does not include a single complete program.

2. The hidden details of processor communication make performance prediction of HPF programs impractical both in theory and practice.

3. Data parallel HPF programs composed of well-structured subroutines are inefficient in terms of time and space. Language and performance limitations make it necessary to replace subroutine calls by the corresponding bodies and local variables by global, distributed vectors. Consequently, existing Fortran programs cannot be made parallel with minimal changes only.

4. HPF ignores the serious problem of race conditions due to parallel interference [H6. 4.2] .

In short, HPF disregards fundamental principles of language design that have been known for decades. As a result HPF does not support the construction of parallel programs that combine simplicity, reliability, and efficiency.

The HPF Handbook claims that "languages prior to HPF forced the programmer to handle nearly all details of communication, leading to complex code, bugs and general frustration" [H0.2].

My experience is the opposite: I find message parallelism much easier to use [4, 6, 12] . HPF is one of the most frustrating programming tools I have ever used. As the HPF designers put it: "A programming tool is not much good if you don't know what a program in the language means" [H0.2], parallel HPF programs composed of well-structured subroutines are inefficient in terms of time and space. Language and performance limitations make it necessary to replace subroutine calls by the corresponding bodies and local variables by global, distributed vectors. Consequently, existing Fortran programs cannot be made parallel with minimal changes only.

Let me finally discuss some questions which others have raised about this evaluation of HPF:

Were the problems encountered due to the limitations of a particular compiler rather than the language itself? I don't think so. The four main criticisms listed above all refer to the inherent limitations of the language and its documentation. However, I fear that HPF fundamentally depends on compile time magic that may not be achievable.

Is it fair to rewrite block structured algorithms in a language that does not support block structure? In the 1960s, Algol 60 and Simula 67 introduced block-structure in modern programming languages. To omit modularity a quarter of a century later is a step backwards in programming technology.

Is HPF mature enough for this type of investigation? If computer programming is a professional discipline, then such an argument is unacceptable. Every software concept that we propose and implement must be open to criticism from the beginning.

Have I failed to give credit to the rationale for HPF? I appreciate that HPF was designed as an attempt to make parallel programming easier. But, after thirty years in parallel programming, I conclude that it fails to achieve that worthy goal and actually makes parallel programming more difficult.

Isn't it possible that HPF can improve over time? Niels Bohr was fond of quoting the Danish humorist, Robert Storm Petersen, who said: "It is difficult to make predictions, especially about the future." For a scientist, wishful thinking is just idle speculation.

If there is a lesson to be learned from HPF, it is this: A small group of designers can strive for conceptual integrity; a working group of 40 people cannot.
