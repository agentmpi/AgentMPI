# Translational Research in the MPICH Project

William Gropp 1 Rajeev Thakur 2 Pavan Balaji 2

1University of Illinois, Urbana, IL 61801, USA 2Argonne National Laboratory, Lemont, IL 60439, USA

## Abstract

The MPICH project is an example of translational research in computer science before that term was well known or even coined. The project began in 1992 as an effort to develop a portable, high-performance implementation of the emerging Message-Passing Interface (MPI) Standard. It has enabled the widespread adoption of MPI as a way to write scalable parallel applications on systems of all sizes including upcoming exascale supercomputers. In this paper, we describe how the translational research process was used in MPICH, how that led to its success, the challenges encountered and lessons learned, and how the process could be applied to other similar projects.

## 1. Introduction

MPI (Message Passing Interface) is a portable, standard API for writing parallel programs using a distributed-memory programming model. MPI began as an effort in 1992 by a group known as the MPI Forum to define a standard API for message passing instead of the plethora of different APIs provided by existing vendor and research message-passing libraries at the time. Version 1.0 of the MPI specification was released in 1994, and MPI has been widely used since then for developing parallel scientific applications on all kinds of parallel computer systems. Several new versions of the specification, with additional features, have been released over the years, the latest being MPI 3.1 in 2015. MPI 4.0 is expected to be released in a year. MPI has been essential to the success of super computing in the past 25 years. It has provided a standard message-passing interface for scalable parallel systems and clusters. It is supported by all supercomputer and cluster vendors, and it is used by essentially all science and engineering parallel simulation codes running on supercomputers and is expected to continue to do so in the next decade. MPICH [14] began as a research project in 1992 with the goal of developing a portable imple mentation of the evolving MPI standard as it was being defined. The idea was to provide early feedback on decisions being made by the MPI Forum and provide an early implementation to allow users to experiment with the specification even as it was being developed. In many cases, the MPI design pushed features for new capabilities not seen in previous systems, and MPICH became the reference implementation that proved that these features can be implemented efficiently. Targets for the implementation included all systems capable of supporting the message-passing model— from single-node, shared-memory systems to clusters of systems and the largest supercomputers in the world. MPICH has been and continues to be the de facto implementation driver leading to the success of MPI. MPICH was always intended as both a research project and a software development project. As a research project, its goal is to explore methods for delivering the highest possible performance for communication in parallel applications on all available hardware. As a software project, its goal is to promote the adoption of the MPI Standard by providing users with a high-quality, high performance implementation on a diversity of platforms, while aiding vendors in providing their own customized implementations. MPICH was designed from the ground up to serve as a reference for other derived implementa tions. It was cleverly layered so that vendors could replace the lowermost “driver” level of MPICH, thus customizing it to their own hardware, while reusing most code. More important, vendors could choose to customize fewer or more layers in MPICH, and all did so. While the full picture is more complex, MPICH has three major layers [6]. The top layer pro vides the implementation of the MPI API and provides code for features that are part of MPI but not critical to performance, such as MPI attributes (a way for software libraries and tools to attach information to MPI objects) and error reporting. The next layer, called the “device,” provides architecture-specific optimizations for performance-critical portions of the MPI interface, including point-to-point communication, collective communication with an arbitrary collection of MPI pro cesses, one-sided (remote-memory) communication, and communication with noncontiguous data. 1 This layer exposes an internal interface called the MPICH Abstract Device Interface (ADI). Each version of MPICH has provided a third layer within the device: a simple network or shared-memory “module” that is required to provide as little as a simple movement of bytes between processes, thus making initial ports to new architectures easy, but is allowed to override as much of the MPI functionality as it desires. All layers have a modular design (based mostly on inlining code and sharing data structures in keeping with the capabilities of compilers and runtimes when MPICH was designed) as well as a focus on low latency. These features allow vendors to take advantage of particular capabilities of their systems, such as hardware support for a subset of collective operations (e.g., the IBM BlueGene for reduction operations (MPI Allreduce) [2]). A full ADI implementation lets vendors optimize nearly the entire stack, leveraging MPICH code to handle the MPI API, internal state, and support for features not critical for performance. This layered design has been key to the longevity of MPICH. Today, most supercomputing vendors use MPICH in order to develop their own proprietary implementation of MPI. MPICH has always had a focus on performance, as nearly all applications make use of paral lelism in order to access performance not otherwise obtainable. Performance in this case includes both low latency (including overhead in the LogP model [3]) as well as high bandwidth of data com munications. One early example was a port of MPICH to the NEC SX-4 vector supercomputer [4]; the layered design made it easy to port to a very different CPU and interconnect architecture. MPICH has continued to evolve over three decades in order to support the evolving MPI stan dard (now over 800 pages long) and new computer architectures. MPICH has continued successfully in its triple role:

• As a reference implementation that supports the latest MPI features as soon as they are standardized.

• As the leading implementation used by vendors (Intel, Cray, Microsoft, Tianhe, Sunway, etc.) for their own products. MPICH-derived implementations are used on practically all the largest supercomputers today as well as on clusters. The popular Intel MPI, Cray MPI, and MVAPICH [15] implementations of MPI are also derived from MPICH.

• As a research platform that is used to study how one can handle large-scale parallelism 1 MPI provides a powerful, efficient, and flexible way to describe many data layouts, including strided and indexed data.

(MPICH has scaled to over 10 million processes) and heavy multithreading and hybrid pro gramming for extreme-scale systems. MPICH won an R&D 100 Award in 2005.

## 2. Translation Process

Translational research is a well-known and well-understood paradigm in the biomedical research
community as a third paradigm of research in addition to the conventional paradigms of founda
tional and applied research. Translational medicine (TM), as it is known, comprises three pillars:
bench (basic research), bedside (applying the basic research to clinical research/trials), and commu
nity (resulting in new practices in patient care). In the computer science field, although examples
of translational research do exist, it is not a widely used or understood concept. Abramson and
Parashar have recently formalized the notion of translational research in computer science, calling
it translational computer science (TCS) [1]. Analogous to the three pillars of bench, bedside, and
community in TM, they define the three pillars of laboratory, locale, and community in TCS. In
a TCS project, basic research done in a hardware or software laboratory is then tested at a lim
ited scale in an appropriate environment before the technology is deployed at a wider scale in the
community.
In MPICH, the research was always meant to be applied as part of the original plan rather than
after the fact. MPICH always intended for research concepts to be embodied in software that is
widely used and widely deployed on systems of all kinds and for applications of all kinds. In that
sense it was always a translational research project, although we did not use (or had even known)
that term. In translational computer science terminology, the “laboratory” for MPICH is the core
set of researchers and developers of MPICH; the “locale” is the set of early users, collaborators, and
vendor partners who tried out alpha and beta versions of each release and provided feedback; and
the “community” is the worldwide community of MPICH users. MPICH was successful because of
the following design choices that were made from the beginning:
• Good software development practices. The code was developed using good software de velopment and engineering practices, including documentation, version control, an extensive test suite, and the use of a bug-tracking system [5]. Robust tools to support these practices were not as available in the 1990s as they are now, so in many cases we built our own. For example, we built a regression-testing framework that would automatically run the entire test suite nightly with different compilers and options—both common choices and random selection of choices, as there were too many combinations to test—on different platforms and display the results on a web page the next morning. We did use available tools where possible, such as GNU autoconf to determine system-specific parameters at build time.
• Designed for performance and customizability. As mentioned in Section 1, MPICH was designed to be modular so that different parts could be replaced with other plug-ins. A key feature was the internal ADI that served as a portability layer. Higher-level MPI features were implemented portably on top of the ADI, and only the ADI needed to be implemented and tuned separately for different platforms and networks. Other features, such as collective communication algorithms, could also be easily replaced. This design enabled vendors to take the MPICH code and easily tune it for their platforms.

• Liberal software license to encourage adoption. Since 1992, MPICH has had a liberal BSD-like software license that enabled vendors to be comfortable in using the source code to derive their own commercial products. In fact, to our knowledge, MPICH was one of the first external open-source software packages that Microsoft adopted for its own use.

• Outreach. We authored several books [8, 9, 11, 10, 7] and gave tutorials at many conferences, such as the annual SC conference, to help increase awareness and adoption of MPI.

The design of MPICH has made it an excellent platform for research into performance and scalability issues in implementing a parallel programming system. For example, many ideas were first explored by students and postdocs who used MPICH as their “experimental testbed.” Many of these efforts have led to best paper awards or best paper finalists [16, 17, 20] and have in fluenced the design and implementation of MPICH. The implementation of MPI-IO in MPICH, ROMIO, was created by one of the authors while a postdoc at Argonne [18, 19]. The translation process was greatly helped by interactions with the community, including the MPI Forum on MPI specification-related issues; MPICH users on issues related to ease of installation and use, correct ness, performance, and scalability; colleagues in the research community on research issues; and vendor partners on all above issues.

## 3. Impact and Lessons learned

MPI and MPICH are still in widespread use 26 years later and are expected to continue to be used in the forseeable future on upcoming exascale computing systems. In fact, the first three exascale systems in the U.S. (Aurora at ANL, Frontier at ORNL, and El Capitan at LLNL) will use MPICH based MPI implementations. The MPICH team collaborates closely with the vendors (Intel and Cray in this case), and the MPI implementations running on those systems will be provided, tuned, and supported by the vendors but using the MPICH code base. Scientific applications of all kinds rely on MPI for distributed-memory parallelism, often together with some other programming model to exploit on-node concurrency (e.g., OpenMP or CUDA). In fact, the success of MPI has made it difficult for other more modern programming approaches to replace MPI: Unless the new approaches are significantly superior in multiple aspects [12], application developers are unwilling to invest the effort in porting their codes to a different programming model or even to trust it. As an example of impact, searching for MPICH on Google Scholar returns over 19,000 items, including papers with hundreds of citations, which is a large number in the parallel computing field. These include papers specifically on MPICH as well as papers that used MPICH as the experimental testbed for other experiments. Many of these papers have been recognized with best paper awards. As an issue with translational research, many papers that make use of MPICH, either directly by using MPICH to provide the parallel programming system or indirectly by using an MPI based on MPICH, do not necessarily cite or otherwise acknowledge MPICH or the team that created MPICH. This makes it more difficult to track the impact of MPICH and to provide clear metrics of the impact. This is a well-known and unsolved problem with citing software used in research [13], which also impacts reproducibility of computational results. Setting clear standards for identifying and acknowledging software, especially open-source software, would benefit everyone. The roadblocks identified in [1] for translational computer science are all valid, and we experi enced many of them ourselves. For example, it is not easy to get sustained funding for a translational research project, because funding agencies are more geared toward funding traditional research. We were fortunate to be funded by the US Department of Energy (DOE) for MPICH, and it contin ues to be funded through DOE’s Exascale Computing Project. One way that work on MPICH was partly funded was as support for applied research projects using MPICH as the experimental testbed. This method is common in other areas of science; for example, complex experimental laboratories often rely in part on funding from different research grants to increase the capability of their facilities and to maintain them. This approach is also efficient for the funding agencies as new work can leverage previous investments. Some of the roadblocks for translational research have not always been present, for example, when MPICH (and the MPI standardization effort) started. Perhaps the biggest challenge has been a change in the timeline for funding, which is now mostly built around short-term (3–5 year) grants and projects. This approach may work if a team has the ideas ready and only needs to implement them, but if the team needs a few years to develop the ideas and iterate with the user communities, this time is not enough. It is even more difficult if the potential is unclear, as was the case for the MPI standard process, which was not the first attempt to create a message passing standard. Another challenge is the artificial separation between basic research and translational research. We believe that the best translational software involves both basic and applied researchers from the beginning through implementation, deployment, and future developments. Finally, no practical mechanism exists to sustain open source software, or, in other words, there is no general business model for supporting the software. Software needs to be maintained and often reimplemented as both the hardware and the system software changes. Someone must bear those costs, but most users simply see open-source software as “free” and do not recognize the costs of providing, maintaining, updating, and optimizing the software.

## 4. Conclusions

Many factors contributed to the success of MPICH as a translational research project. First and foremost, the quality of the MPI Standard itself played a big role—not just the functionality, but its focus on performance and support for libraries. Secondly, the design of MPICH for adoption by others enabled vendors to provide optimized implementations for their platforms, which helped in making it widely available on production systems. We also spent a lot of effort on documentation and training, which helped educate users not just on how to use MPI but how to use it in a way that delivers high performance. We also “listened” to our users on the MPICH discussion list, responded to their bug reports, and incorporated their suggestions. These are lessons that we feel apply to any software project, and while they may seem obvious, are often missed in practice. This is not to minimize the usual elements, such as good software engineering in design, implementation, and testing. Rather, having a clear specification devised with open community input, a design targeting the needs of those that would adopt the software, and a continuous process to listen to and learn from users are, in our opinion, essential components of developing an effective translational software project. Finally, despite the successes of MPICH, we feel that if we had to start a similar new project today, it would be difficult. The MPICH project was started in a different era under different circumstances. As noted in [1], the funding models in existence today are, in general, not conducive to starting a new long-term translational research project. However, we hope funding agencies would notice the opportunity and value of such activity and support long-term translational research.
