[2206.14285] Lessons Learned on MPI+Threads Communication

# Lessons Learned on MPI+Threads Communication

Rohit Zambre, Aparna Chandramowlishwaran Electrical Engineering and Computer Science University of California, Irvine Irvine, CA, USA {rzambre,amowli}@uci.edu

###### Abstract

Hybrid MPI+threads programming is gaining prominence, but, in practice, applications perform slower with it compared to the MPI everywhere model. The most critical challenge to the parallel efficiency of MPI+threads applications is slow MPI_THREAD_MULTIPLE performance. MPI libraries have recently made significant strides on this front, but to exploit their capabilities, users must expose the communication parallelism in their MPI+threads applications. Recent studies show that MPI 4.0 provides users with new performance-oriented options to do so, but our evaluation of these new mechanisms shows that they pose several challenges. An alternative design is MPI Endpoints. In this paper, we present a comparison of the different designs from the perspective of MPI’s end-users: domain scientists and application developers. We evaluate the mechanisms on metrics beyond performance such as usability, scope, and portability. Based on the lessons learned, we make a case for a future direction.

###### Index Terms:

exascale MPI, MPI Endpoints, MPI+OpenMP, MPI+threads, MPI_THREAD_MULTIPLE, partitioned communication, network parallelism

## I Introduction

The hybrid MPI+threads model is gaining prominence over the traditional MPI everywhere approach following the evolution of modern computing architectures. Over the last decade, the number of cores on a processor has grown disproportionately to the growth in other on-node resources such as memory, TLB space, and network resources (work queues and doorbell registers) [2, 59]. Consequently, domain scientists have witnessed their applications run out of memory with the memory-hungry MPI everywhere model on large problem sizes [48, 21, 51]. With MPI+threads (e.g., MPI+OpenMP), on the other hand, applications are able to scale to much larger problems since the model enables users to utilize the many cores on a processor with threads and efficiently share the limited on-node resources between cores with a single process per node (or NUMA domain). For these reasons, modern event-based frameworks (e.g., Legion [18] and YGM [50]) have not been developed with MPI everywhere from the start.

In terms of performance, however, MPI+threads applications tend to perform slower than their MPI everywhere counterparts in practice [44, 21, 38, 48]. The reason is that MPI+threads programming raises many new challenges, such as mitigating thread-synchronization overheads [37, 53, 43], and preventing performance-degrading memory accesses (e.g., false sharing), that are not present in MPI everywhere. The most critical challenge, however, is the dismal communication performance of MPI+threads applications [68, 14, 59, 13, 16]. This challenge is a pressing bottleneck because most scientific simulation campaigns run close to the strong-scaling limit where communication has been demonstrated to occupy a significant portion of an application’s runtime [52, 54, 63, 62].

Furthermore, as an application approaches the strong-scaling limit, the size of each individual message decreases, and the communication performance is limited by the rate of issuing messages rather than the network bandwidth. In this paradigm, the interoperability of threads with MPI is critical for the performance of an MPI+threads application.

MPI defines multiple levels of threading support going from a highly restrictive level—only one thread will execute—to a completely flexible level: multiple threads can execute MPI operations in parallel (i.e., MPI_THREAD_MULTIPLE). According to a 2017 survey of applications chosen as candidates for the upcoming exascale systems and other application development reports, domain scientists prefer using the flexible MPI_THREAD_MULTIPLE level but do not do so currently primarily because of poor performance [19, 24, 12].

Recently (starting in 2019), however, MPI libraries have made significant strides in achieving scalable multithreaded communication performance that matches that of MPI everywhere. Figure 1(a) shows MPICH’s support for high-speed MPI_THREAD_MULTIPLE performance in its latest 4.0 release as an example. The primary factor for this improved performance is the MPI library’s ability to map logically parallel communication—operations that are not ordered according to MPI’s semantics—to the underlying network parallelism [66, 67, 49, 4]. With such new capabilities, applications are able to achieve the best of both worlds—high scalability and high performance—with MPI+threads compared to MPI everywhere. Figures 1(b) and 1(c) demonstrate the performance impact of using logically parallel communication for traditional stencil-style workloads (Uintah computational framework [54, 68]) and modern data-centric workloads (Legion-based Circuit simulation [18, 68]).

In any application, the key to achieving fast MPI+threads communication is logically parallel communication. Without it, the new MPI libraries are ineffective. So, how can domain scientists and application developers expose such communication parallelism?

In this regard, the MPI community first pursued user-visible extensions to the standard in the form of MPI Endpoints [31, 26, 28]. An endpoint represents a logically independent stream of communication. Each endpoint is directly addressable through an MPI rank, making user-visible endpoints a flexible solution. The MPI Forum had deliberated the MPI Endpoints proposal but ultimately suspended it on the prospect that existing MPI objects such as communicators and windows can expose the same level of logical communication parallelism as user-visible endpoints. In cases where MPI’s semantics prevent users from exposing communication independence, this school of thought advocates the use of MPI Info hints to relax the limiting MPI semantics which would allow the application to expose logically parallel communication through alternative MPI mechanisms like tags. To analyze the performance differences between the two approaches, recent studies map the capabilities of both to parallel network resources and evaluate them on applications from different domains: linear system solvers, graph analytics, astrophysics, particle physics, and event-based runtimes. These studies demonstrate that existing MPI mechanisms indeed perform as well as user-visible endpoints [67, 68], and they are the basis for the introduction of new hints for application-specific relaxation of semantics in the latest MPI 4.0 standard.

Figure 1: MPI+threads achieves high scalability and high performance with logically parallel communication on new MPI libraries. In this paper, we show that exposing the communication independence between threads with existing MPI objects has various drawbacks even with the new Info hints. Using communicators, the most explicit existing mechanism, to expose communication independence is quite complex even for applications with well-structured and regular communication patterns (e.g., stencil workloads). The complexity arises from the fact that users need to ensure messages are matched appropriately while expressing communication parallelism. This complexity hurts not just the productivity of the domain scientist but also the MPI library’s mapping to the underlying network parallelism, thereby hurting performance. Relaxing the unneeded MPI semantics through Info hints and expressing communication parallelism through tags instead is one way to combat this complexity, but such a solution is not portable since the optimal mapping to the parallel network resources is dependent on hints specific to an MPI library.

On the other hand, for the same applications, we find that the user-visible endpoints solution is not only portable but also straightforward because of the flexibility of its design: each endpoint is directly addressable. Like the idea of “ports” first described by Foster et al. [31, 26], endpoints do not constrain communication parallelism information with existing MPI semantics. The concern here, however, is the introduction of a new concept to the user. Presumably, this concern does not hold with existing MPI mechanisms since users are already aware of communicators, windows, etc. However, we argue that MPI users do not intuitively think of existing MPI objects as means of expressing parallelism. For example, users have historically viewed a communicator as a group of processes. That it can double up as a means to express logically parallel communication is a corollary of its definition. Hence, the concern of enforcing new concepts (i.e., repurposing existing MPI objects) on users also holds for existing MPI mechanisms.

Finally, the MPI 4.0 standard also introduced partitioned operations as an alternative to MPI Endpoints to alleviate the performance problem of MPI+threads communication. This new interface allows users to define a persistent message with multiple data partitions so that each thread can drive different partitions of a single message. Ongoing research on this new interface demonstrates that partitioned communication does perform better than MPI+threads communication with no logically parallel communication (“MPI+threads (Original)” in Figure 1) [30, 65, 17, 34], but a performance analysis against the other two mechanisms, especially in its capabilities to utilize the underlying network parallelism, remains to be seen. We note, however, that the partitioned interface exhibits certain semantic limitations which could prevent it from matching the performance of the other approaches. For example, threads share the single MPI request of a partitioned message (see Section II-C) which means that threads would contend to access the shared request’s resources in the MPI library, or that threads would need to synchronize to allow only one thread to poll for completion. In either case, the application is prone to incur overheads of contention or synchronization compared to fully independent paths. Techniques like double or triple buffering could partially mitigate the slowdowns caused by this limitation, but they do not allow threads to achieve complete independence in a manner that the other mechanisms allow and promote.

Out of the three approaches, two have been introduced in MPI 4.0 and at least one of them allows users to expose complete independence between threads. So, does this mean MPI’s end users are satisfied? As is the case with the success of any technology, the answer lies with the end users, the domain scientists. We show that MPI 4.0 does not meet the needs of MPI+threads applications, and that it introduces new problems. The current solutions in MPI 4.0 may be stepping stones to alleviating the performance of MPI+threads communication, but they are not sufficient by themselves.

In this paper, we compare the strengths and limitations of the designs (described in Section II) with respect to their applicability to MPI’s point-to-point, RMA, and collective communication. Our comparison (see Section III) is centered around the lessons learned from evaluating a variety of different types of MPI+threads applications. Guided by both quantitative (in [67, 68]) and qualitative (this paper) comparisons of the different interfaces, in Section IV, we discuss a future direction that would enable applications to achieve not just high scalability and performance, but also high productivity with the MPI+threads programming model.

## II The Three Designs for MPI+Threads Communication

In this section, we describe how the three designs can expose communication independence between threads, and discuss their motivations and their implementation evaluations.

### II-A Existing MPI mechanisms

With existing MPI objects, such as communicators, tags, and windows, users can expose relatively unordered operations for all types: point-to-point, RMA, and collectives.

Communicators apply to collective and point-to-point communication. For the former, MPI requires collectives to be issued serially on a communicator. Hence, users can issue collectives in parallel on a process only on distinct communicators. For two-sided operations, MPI specifies a nonovertaking order and uses the $\langle$ communicator, rank, tag $\rangle$ triplet to match operations. Two or more operations issued using different communicators cannot match the same target operation and hence imply no relative ordering; such operations are logically parallel. Operations that share a communicator but use different ranks or tags, however, are not logically parallel because of the possibility of wildcards (e.g., MPI_ANY_TAG) on the receive side. Hence, the only way to expose logical communication independence for point-to-point operations with MPI’s default semantics is through the use of multiple communicators.

Tags with hints. MPI 4.0 features new Info hints that allow an application to relax semantics it does not need. Info hints relevant to this paper include mpi_assert_allow_overtaking, mpi_assert_no_any_tag, and mpi_assert_no_any_source. The first, when set, informs the MPI library that the operations do not need to be matched in the order that they were posted. This Info hint is beneficial when the application requires wildcards but does not require the MPI library to maintain the order of matching. With the nonovertaking order relaxed, two or more send operations using different tags are logically parallel even if they use the same communicator and address the same target process. Because of wildcards, however, similar receive operations are not logically parallel. If the application does not require wildcards, the domain scientist can set the other two hints to relax the wildcard’s constraints. Without any wildcards, two or more operations (both send and receive) that use the same communicator, address the same process, but use different tags can never match with the same target operation. Hence, such operations are logically parallel.

Windows apply to MPI’s RMA operations. By default, MPI maintains program order only for its atomic operations (e.g., MPI_Accumulate) originating from the same source and targeting the same memory location on the same window. Otherwise, both atomic and nonatomic RMA operations (e.g., MPI_Put) on different windows are unordered. Although nonatomic operations are logically parallel in any case, users need to be wary of mixing synchronization and initiation operations in parallel on the same window. For example, if one thread is waiting inside MPI_Win_flush and another continuously issues MPI_Get operations, the first thread might block indefinitely. To overcome such cases and explicitly expose parallelism for any type of RMA operation, users have the option of using distinct windows for different threads.

By mapping the communication independence exposed by the above mechanisms to the underlying network parallelism, recent research demonstrates that MPI+threads applications can indeed achieve scaling communication throughput that matches that of MPI everywhere [67, 68, 49]

### II-B User-visible Endpoints

Researchers had initially proposed to extend the MPI standard to introduce user-visible MPI endpoints [28]. With a new API, users can create communicators with multiple endpoints (see Figure 2). This API creates a new communicator (context ID) from an existing one, parent_comm, and provides my_num_ep number of handles to the new communicator. Each handle is addressable with a distinct rank. For all operations, users would specify the local endpoint to use using one of the returned handles (new_comm_handles) and address a target endpoint using the endpoint’s rank, a global index of the endpoint, making endpoints a flexible interface. One could then use an endpoints communicator to create endpoints for other MPI objects such as windows and files [5].

Figure 2: API to create a communicator with multiple endpoints.

1MPI_Comm_create_endpoints(parent_comm, my_num_ep, info, new_comm_handles)

Each endpoint takes on the semantics of an MPI rank. Like messages originating from different processes, messages from different endpoints are unordered and hence logically parallel. If the user maps each thread to a distinct endpoint, then all threads are directly addressable. Given their flexible interface, user-visible endpoints represent the upper bound in expressing the communication parallelism available in an application. Several efforts show scaling multithreaded communication throughput with user-visible endpoints [58, 29, 40].

One of the notions on which the endpoints proposal was suspended was that some networking hardware may not be able to optimize the creation of new network addresses (for new endpoints) after initializing the MPI library [29]. We note, however, that the new MPI libraries have addressed this problem by creating a pool of network resources during the initialization phase [49, 67]. Such implementations then map logical entities like endpoints to physical network resources.

### II-C Partitioned Communication

MPI 4.0’s partitioned communication interface allows users to specify a persistent message with multiple partitions. Each partition contributes to a single message, and the contributions could occur in parallel from multiple threads. Users define the operation’s characteristics (e.g., number of partitions, tag, etc.) outside the critical path, and then contribute the individual partitions of the message whenever a thread is ready to communicate (see Figure 3). MPI 4.0 contains APIs to describe standard-mode send and receive operations only, but the idea can extend to other modes of point-to-point operations and even RMA and collective operations [41]. These extensions will require their own set of APIs to define the partitioned communication equivalent for each operation.

Partitioned communication was introduced to combat the message-matching overheads in multithreaded communication. Message matching is a costly serial operation [56]. If $n$ threads use the same communicator (“MPI+threads (Original)” in Figure 1), the overhead of message matching grows by $O(n)$ . Since partitioned operations share a persistent message, they incur a message matching overhead of only $O(1)$ for $n$ threads driving the multiple partitions of the message. Research implementations have demonstrated performance benefits of partitioned operations especially for large partitions even with older MPI libraries that do not capitalize on parallel network resources [34, 30]. Partitioned operations are suited to benefit from the capabilities of the new MPI libraries (multiple partitions could map to distinct network resources), but such a study has not been conducted yet. More important, how partitioned operations compare to the other mechanisms of exposing logically parallel communication where message matching is not a concern (due to a distinct matching engine per communication channel [49, 67]) remains to be seen.

## III Application-Centric Comparisons of The Three Designs

In this section, we discuss how the different designs (see Section II) compare against each other with respect to two key metrics: ease of use (which reflects the productivity of domain scientists), and applicability to different MPI operations (which measures the scope of the designs). We map the communication patterns of key applications to the different design choices to make such a comparison. In the process of doing so, we collaborate with application developers from a variety of institutions including University of Utah (stencil communication in the hypre linear solver used by Uintah [54]), Maison de la Simulation (stencil communication in Smilei [27]), Pacific Northwest National Laboratory (graph communication in Vite [33]), University of California, Irvine (stencil communication in Pencil [63]), HPE (RMA communication in WOMBAT [47]), and Argonne National Laboratory (Legion’s MPI backend [6]). We organize our discussion below by the lessons learned from comparing the different designs.

### III-A Point-to-point communication

Mechanism 1: Communicators. Using distinct communicators is the most explicit way to express logically parallel communication for point-to-point operations with MPI’s default semantics (see Section II-A). We discover, however, that communicators pose several challenges: complexity, high resource usage, and lack for flexibility for irregular and dynamic communication patterns. We detail our lessons learned below.

\MakeFramed\FrameRestore

Lesson 1: Exposing logically parallel communication with communicators is a complex task due to its matching requirements. \endMakeFramed

To understand the first lesson, let us consider a relatively simple example of a static (communication pattern of each thread is fixed) 2D 9-point stencil. Figure 4 shows the ideal communicator usage—minimum number of communicators with all of the available parallelism exposed—for such a communication pattern. For a given direction of communication, we have as many communicators as there are communicating threads on the edge (a plane in 3D) since the operations of the threads are independent. The threads on a corner, however, use a single communicator for all directions since their operations for the different directions occur serially. The mapping of communicators to threads is not the same on each process. For example, thread 7 of the bottom-left process in Figure 4 must use a communicator for its north-south communication that is different from the communicator that thread 7 on the top-left rank uses for the same north-south direction. This difference in communicators prevent threads 1 and 7 on a process from using the same communicator and serializing their communication. In other words, given a map of communicators for the threads of a given process, the map for other processes can be derived by mirroring the map along the change in cartesian coordinates of the process. Listing LABEL:code:stencil_using_comms shows a 2D MPI+OpenMP 5-point stencil that exposes communication parallelism using communicators. For simplicity, it does not optimize communicator usage for corner threads. Lines 23–26 demonstrate the mirroring of communicator assignment to threads. This mirroring idea extends to the diagonal exchange in 9-point stencil as well: the user would need to extend lines 12–17 to create 4 additional sets of communicators—2 diagonals along the NS boundaries and 2 along the EW boundaries—each containing as many threads as there on the edge. Combining the mirroring strategy with the optimization to use a single communicator for corner threads will achieve the map illustrated in Figure 4 but at the cost of further complexity. The user would need to extend lines 23–24 to mirror the assignment of communicators to threads along both axes for all directions of exchange. Diagonal communicator sets require another dimension of mirroring that is exemplified by thread 1 on the bottom left process (see Figure 4) using the same communicator for its NE exchange as does thread 1 on the bottom right process for its NW exchange. Optimizing for reduced communicator usage is important for efficient use of network resources (see Lesson 3 below).

\MakeFramed\FrameRestore

Lesson 2: Using communicators to expose communication parallelism is not intuitive. \endMakeFramed

Continuing on the 2D 9-point stencil example, the intuitive approach to expose communication parallelism is to create as many communicators as there are threads and then use communicator $i$ for thread $i$ ’s send operations and communicator $j$ for thread $i$ ’s receive operations where $j$ is the thread id of the remote thread that thread $i$ is receiving from. This usage of communicators is correct, but it exposes only half of the available parallelism. The communication of adjacent threads on an edge occur in parallel but the operations of threads on opposite edges use the same communicator. For example, in Figure 4, thread 1’s send operation uses communicator 1, which thread 7 also uses for its receive operations.

114using␣distinct␣communicators,␣but␣the␣polling␣thread␣is␣forced

115to␣iterate␣over␣the␣communicators␣to␣process␣all␣incoming␣messages.

116Thus,␣on␣a␣single␣node,␣the␣polling␣thread␣conflicts␣with␣the

117communicators␣of␣the␣task␣threads.␣The␣polling␣thread␣relies

118on␣wildcards,␣and␣hence␣using␣partitioned␣operations␣for␣this

119communication␣pattern␣is␣not␣straightforward.␣With␣endpoints,

120on␣the␣other␣hand,␣the␣polling␣thread␣can␣use␣a␣distinct␣endpoint,

121use␣wildcards,␣and␣satisfy␣matching␣requirements.

122Prior␣evaluations␣show␣that␣Legion’s polling thread processes

123events 1.63× slower with communicators than with

124endpoints~\cite{zambre2021logically}.

143%\subsubsection{Mechanism␣2:␣Tags␣with␣hints}

144\minititle{Mechanism␣2:␣Tags␣with␣hints.}

145The␣new␣Info␣hints␣in␣MPI␣4.0␣allow␣domain␣scientists

146to␣use␣tags␣instead␣of␣communicators

147to␣express␣logical␣parallelism␣in␣applications␣that

148do␣not␣use␣certain␣MPI␣semantics␣(see␣\secref{sec:existing_mechanisms}).

149Tags␣bypass␣some␣of␣the␣challenges␣with␣communicators,

150but␣introduce␣new␣ones.␣We␣describe␣the␣lessons␣learned

151from␣using␣tags␣below.

152

153\begin{concern}

154␣␣␣␣␣␣␣␣\emph{Lesson␣6:}␣Using␣tags␣for␣communication

155␣␣␣␣␣␣␣␣parallelism␣is␣intuitive.

156\end{concern}

157

158Most␣\threads{}␣applications␣that␣use

159\multiple{}␣already␣encode␣thread␣IDs␣into␣the␣tags␣of

160their␣communication␣to␣differentiate␣operations␣that

161target␣different␣threads␣on␣the␣same␣target␣process

162(\eg{},␣hypre␣and␣Smilei),␣indicating␣that

163domain␣scientists␣intuitively␣think␣of␣tags␣as␣a␣means

164of␣expressing␣logical␣parallelism.␣Hence,␣the␣approach␣of␣using

165tags␣requires␣the␣least␣amount␣of

166changes␣to␣existing␣applications.␣These␣changes␣would

167only␣be␣in␣the␣form␣of␣creating␣a␣new␣communicator

168with␣Info␣hints␣that␣relax␣unneeded␣MPI␣semantics

169(see␣\coderef{code:using_tags}).

170

171\begin{concern}

172␣␣␣␣␣␣␣␣\emph{Lesson␣7:}␣Achieving␣optimal␣multithreaded

173␣␣␣␣␣␣␣␣communication␣performance␣with␣tags␣is␣tedious.

174\end{concern}

176%\miniminititle{Intricate␣use␣of␣tags.}

177Even

178though␣tags␣and␣communicators␣have␣the␣same

179matching␣constraints,␣tags␣can␣provide␣more

180information.␣Consider␣the␣MPICH␣library␣that

181features␣multiple␣virtual␣communication␣interfaces

182(VCIs:␣network␣communication␣channels␣mapping

183to␣distinct␣network␣hardware␣contexts)~\cite{zambre2020learned},

184and␣the␣hypre␣library␣that␣encodes␣the␣IDs␣of␣the

185sending␣and␣receiving␣threads␣into␣the␣tag␣along

186with␣other␣application-related␣information.

187The␣thread␣IDs␣in␣the␣tag␣provide␣information

188about␣which␣local␣and␣remote␣VCI␣to␣use.

189But␣if␣MPICH␣does␣not␣know␣which␣bits␣of␣the␣tag

190encode␣communication␣parallelism␣information,

191then␣hypre␣is␣at␣the␣mercy␣of␣how␣MPICH␣hashes

192the␣tags␣into␣the␣multiple␣VCIs␣allocated␣to␣the

193communicator.␣Achieving␣the␣optimal␣mapping␣to

194VCIs␣requires␣hypre␣to␣inform␣MPICH␣which␣bits

195encode␣the␣sender’s thread ID, which bits encode

196the receiver’s␣thread␣ID,␣and␣␣how␣to␣map␣the␣bits

197to␣the␣underlying␣VCIs.␣For␣example,␣with␣a␣one-to-one

198mapping,␣MPICH␣can␣use␣the

199sender-thread-bits␣to␣map␣to␣a␣VCI␣on␣the␣host

200process␣and␣the␣receiver-thread-bits␣to␣decide

201which␣VCI␣to␣target␣on␣the␣remote␣process.

202Such␣intricate␣use␣of␣tags␣requires␣domain␣scientists␣to␣learn␣about

203the␣Info␣hints␣that␣are␣specific␣to␣an␣MPI␣library

204(see␣lines␣6--9␣in␣\coderef{code:using_tags}).

4\begin{concern}

5 \emph{Lesson 8:} Programs that use tags for

6 communication parallelism may not be portable

7 across MPI libraries.

8\end{concern}

9

10%\miniminititle{Lack of portability.}

11As discussed above, achieving a high level

12of control and flexibility with tags requires a careful

13use of implementation-specific Info hints.

14It is likely that different MPI implementations

15will support tag-based and communicator-based

16mechanisms of exposing parallelism in different

17ways (VCIs are specific to MPICH; CRIs are specific to Open MPI~\cite{patinyasakdikul2019give}). Since HPC

18application developers are geared towards

19performance-oriented codes, they are compelled

20to adopt Info hints to optimally expose logically

21parallel communication to an MPI implementation.

22Hence, existing MPI mechanisms can result in

23reduced portability of codes which is highly undesirable.

24

25\begin{concern}

26 \emph{Lesson 9:} Encoding communication

27 parallelism in tags is limited by their existing

28 use cases.

29\end{concern}

30

31%\miniminititle{Limited by existing use of tags.}

32End

33users already use MPI tags for

34application-related information. Since the number

35of bits in a tag is limited, an application may not be

36able to encode further parallelism information into

37the tag. Encoding parallelism information with

38lesser-than-ideal number of bits is bound to hurt

39performance.

40Although we have not encountered first-hand an

41application that faces such a problem, others

42have reported running into tag-overflow issues

43on prominent applications (\eg{}, SNAP~\cite{snaptag},

44Smilei~\cite{smileitag}, and MITgcm~\cite{gcmtag}).

45Such reports indicate that applications already use

46a large portion of the tag space; encoding

47parallelism information into tags exacerbates the

48tag-overflow problem.

50%\subsubsection{Mechanism 3: User-Visible Endpoints}

51\minititle{Mechanism 3: User-Visible Endpoints.}

52Given their flexible interface (see \secref{sec:endpoints}),

53endpoints combat the various concerns

54associated with communicators and tags to expose

55logically parallel point-to-point operations.

56Below, we delineate the lessons learned from mapping

57endpoints to different communication patterns.

58

59\begin{concern}

60 \emph{Lesson 10:} Endpoints are intuitive to use.

61\end{concern}

62%\miniminititle{Endpoints are intuitive.}

63Endpoints are an easier alternative to express

64communication parallelism even for patterns such as

65a 3D 27-point stencil

66since each local endpoint can flexibly

67address any other endpoint through a global endpoint rank.

68They are more intuitive

69to use than communicators because application

70developers are innately familiar with the semantics

71of traditional MPI ranks. Users

72express communication parallelism by

73communicating between endpoints as they

74do for MPI ranks in \everywhere{} programming.

75Lines 17--20 in \coderef{code:stencil_using_eps}

76shows this MPI-everywhere like addressing in a

772D MPI+OpenMP 5-pt stencil that exposes

78communication parallelism with endpoints.

79In

80fact, endpoints provide a level of flexibility beyond \everywhere{}:

81threads are not bound to an endpoint. In other words,

82endpoints do not enforce an association between threads and

83the data they work on; a thread is free to

84use any endpoint at any time. Thus, endpoints map

85well to tasking frameworks like OpenMP Tasks~\cite{de2018ongoing}.

86

87\begin{concern}

88 \emph{Lesson 11:} Endpoints distinguish between

89 matching and parallelism information and thus

90 apply seamlessly to all types of communication

91 patterns.

92\end{concern}

93

94%\miniminititle{Endpoints separate matching and

95% parallelism information.}

96Unlike existing MPI mechanisms, user-visible

97endpoints separate the task of expressing

98communication parallelism from the task of

99matching operations. Thus, using endpoints is

100straightforward even for irregular communication

101patterns, such as those of Legion applications (see \figref{fig:legion_comm}).

102Endpoints can flexibly adapt to dynamically

103changing communication neighborhoods because

104threads can address new remote endpoints

105while using the same local endpoint

106(lines 22--25 in \coderef{code:stencil_using_eps}).

107Additionally, endpoints do not suffer from

108overloaded definitions of existing MPI objects. Users do not

109need to compromise on the application’s␣existing␣use

110of␣communicators␣or␣tags.

4\begin{concern}

5 \emph{Lesson 12:} Endpoints lead to efficient

6 resource usage and provide optimal

7 mapping information without sacrificing

8 portability.

9\end{concern}

10

11%\miniminititle{No mismatch in expected mapping to

12% network parallelism.}

13By creating an endpoints communicator,

14users explicitly inform the MPI library

15that the new communicator is

16for the purposes of exposing communication parallelism.

17This information is baked into the API

18unlike the implementation-specific solution of

19using hints with communicators or tags.

20This is why endpoints do not suffer from

21high resource requirements either. In the prior example

22of executing hypre’s␣3D␣27-point␣stencil␣on␣a␣64-core

23processor,␣users␣need␣to␣create␣only␣as␣many␣endpoints

24as␣there␣are␣communicating␣threads,␣which␣is␣56,

2514.4×␣fewer␣than␣that␣required␣by

26communicators.␣Furthermore,␣the␣endpoints

27mechanism␣directly␣provides␣the␣MPI

28library␣with␣all␣the␣information␣needed␣to

29optimally␣map␣to␣the␣underlying␣network

30resources␣unlike␣the␣tag-based␣mechanism

31which␣requires␣the␣application␣to␣inform␣the␣MPI

32library␣about␣the␣specific␣tag␣bits␣that␣encode

33logical␣parallelism␣information.␣Since␣the

34optimal␣mapping␣information␣can␣be␣derived

35from␣a␣standardized␣interface,␣applications

36would␣be␣portable␣across␣MPI␣implementations.

37

38%\miniminititle{(Almost)␣No␣mismatch␣in␣expected␣mapping␣to

39%␣␣␣␣␣␣␣network␣parallelism.}

40%User-visible␣endpoints,

41%however,␣do␣not␣completely␣eliminate␣the

42%potential␣for␣a␣mismatch;␣domain␣scientists␣could␣create

43%more␣endpoints␣than␣the␣number␣of␣underlying

44%network␣resources.␣In␣such␣a␣scenario,␣some␣of

45%the␣distinct␣endpoints␣would␣contend␣on␣the

46%underlying␣network␣resources␣and␣incur␣overheads

47%of␣thread␣synchronization.␣Although

48%we␣have␣not␣come␣across␣an␣application␣that

49%would␣result␣in␣such␣a␣scenario,␣we␣note␣that␣even␣if␣an

50%application’s communication pattern requires

51%more endpoints than the number of network

52%resources, the mismatch problem would hold

53%even with other mechanisms.

56%The MPI Endpoints effort

57%encourages standardizing the concept

58%of endpoints through a new API. With a standardized

59%interface that provides all the information

60%that an MPI library needs to optimally map logically

61%parallel communication to the underlying network

62%parallelism, applications would be portable across

65\minititle{Mechanism 4: Partitioned Communication.}

66MPI 4.0 introduced the new semantics of partitioned

67operations for multithreaded point-to-point communication (see \secref{sec:pc}).

68Like endpoints, partitioned operations promote portability,

69but their semantics can limit exposure of parallelism in

70irregular and dynamic communication patterns. We

71expand on our lessons learned with partitioned operations

72below.

73

74\begin{concern}

75 \emph{Lesson 13:} Partitioned

76 operations do not overload existing definitions,

77 and they promote portability of codes.

78\end{concern}

79

80Partitioned operations provide the same benefits

81as user-visible endpoints on two fronts: (a) they do

82not overload the definitions of existing MPI objects

83and hence minimize the mismatch in expected mapping to

84network parallelism; (b) they promote

85portability of applications across MPI implementations

86by their standardization. Unlike endpoints that

87build on top of existing MPI semantics, partitioned

88operations introduce new semantics. Given that research

89on partitioned operations is ongoing, the usability of

90partitions remains to be seen.

78\subsection{RMA communication}

79\label{sec:rma}

80

81One-sided RMA have no matching semantics. Here, existing

82MPI mechanisms and user-visible endpoints are

83equally straightforward to use, but they each have

84unique concerns. The efficacy of partitioned

85operations for one-sided communication is yet

86to be studied.

87

88\begin{concern}

89 \emph{Lesson 16:} Where the semantics of existing MPI

90 mechanisms limit the exposure of logically parallel atomic

91 operations, those of endpoints achieve optimal mapping

92 of operations to the underlying network parallelism.

93\end{concern}

94

95%\miniminititle{Limiting semantics of existing

96% MPI mechanisms for atomic operations.}

97Using windows to

98expose communication parallelism constrains the

99parallelism information with MPI’s␣atomicity

100semantics.␣This␣constraint␣limits␣the␣user␣from

101explicitly␣exposing␣logically␣parallel␣atomic

102operations␣within␣a␣single␣window␣even␣when␣the

103application␣does␣not␣need␣them␣to␣be␣ordered.

104Consider␣NWChem’s get-compute-update pattern

105for its block-sparse matrix multiplication~\cite{si2015scaling,zambre2020learned}

106where a thread uses \mpiget{} operations

107to retrieve the tiles it needs and, after the multiplication,

108uses an \mpiaccum{} operation to update the

109destination tile (see \figref{fig:bspmm_comm}).

110The \mpiaccum{} operations in a multithreaded

111process must use a single window

112for correct atomicity. Even though these

113parallel operations are

114independent, users have no

115way to explicitly expose this parallelism. The best they

116can do is relax MPI’s

117ordering␣constraint␣(\texttt{accumulate\_ordering=none})

118and␣rely␣on␣the␣MPI␣library’s hashing policies

119to map operations to parallel network channels.

120Any hashing policy, however, is prone

121to collisions and will prevent some operations

122from mapping to distinct network channels.

123With user-visible endpoints, on the other

124hand, users can use multiple endpoints

125within a single window to expose communication

126parallelism \emph{and}

127maintain atomicity.

128

129%User-visible endpoints

130%decouple the task of exposing parallelism from

131%the purposes (\eg{}, atomicity) of existing MPI

132%mechanisms.

133

134\begin{concern}

135 \emph{Lesson 17:}

136 There exists preconceived notions in the MPI community

137 about endpoints being direct handles to network

138 resources.

139\end{concern}

140

141%\miniminititle{Preconceived notions

142% about user-visible endpoints.}

143%A concern that

144%came up during our collaboration with

145%developers of WOMBAT~\cite{mendygral2017wombat}

146A common misconception in the MPI community

147is to view endpoints as

148direct handles to network resources. This

149concern holds not just for RMA operations but

150also for point-to-point operations.

151As a result, the endpoints

152design is sometimes incorrectly regarded as

153a way for MPI libraries to dump the

154responsibility of managing network resources

155on the domain scientist which would in turn

156reduce the portability of applications.

157One explanation for this concern is the usage of the

158term ‘‘endpoints,"␣which␣is␣typically␣associated␣with

159‘‘network␣endpoints." The fact that user-visible

160endpoints were introduced for the purposes of utilizing

161network parallelism is likely to have exacerbated

162the misconception. User-visible endpoints are \emph{not}

163handles to network resources, rather they are a means

164to flexibly express communication parallelism. Their

165usage is separate from the MPI library’s␣task␣to␣map

166the␣exposed␣parallelism␣to␣the␣underlying␣parallel

167network␣resources.␣With␣the␣endpoints␣solutions,

168applications␣would␣create␣as␣many␣endpoints␣as

169there␣are␣streams␣of␣logically␣parallel␣communication.

170The␣MPI␣library␣would␣then␣funnel␣the␣streams␣of

171logically␣parallel␣communication␣on␣distinct

172network␣hardware␣contexts␣depending␣on␣their

173availability.

201\subsection{Collective␣communication}

202\label{sec:coll}

203

204Research␣towards␣implementing

205collectives␣in␣a␣hybrid␣\threads{}␣environment

206has␣primarily␣revolved␣around␣hierarchical

207algorithms␣where␣threads␣first␣implement␣the

208collective␣(\eg{},␣allreduce)␣amongst␣themselves

209and␣then␣one␣thread␣on␣each␣node␣participates

210in␣the␣internode␣collective~\cite{li2013numa,zhou2020collectives}.

211Recent␣studies␣using␣a␣fast␣\threads{}␣library␣(Intel

212MPI␣2019~\cite{intelmpi}),␣however,␣demonstrate␣performance

213benefits␣when␣multiple␣threads␣drive␣a␣collective

214in␣parallel~\cite{wende2019openmp,boyle2017accelerating}.

215Although␣existing␣MPI␣semantics␣require␣collectives

216on␣a␣communicator␣to␣be␣issued␣serially,

217applications␣may␣partition␣the

218collective-data␣of␣a␣process␣across␣threads␣and␣issue

219parallel␣collectives␣on␣the␣different␣data␣segments

220using␣a␣distinct␣communicator␣for␣each

221thread␣(\eg{},␣VASP␣collectives␣observe␣a␣speedup

222of␣over␣2×␣with␣such␣an␣approach~\cite{wende2019openmp}).

223

224\begin{concern}

225␣␣␣␣␣␣␣␣\emph{Lesson␣18:}␣Users␣need␣to␣perform␣the␣intranode

226␣␣␣␣␣␣␣␣portion␣of␣a␣collective␣with␣existing␣MPI␣mechanisms,

227␣␣␣␣␣␣␣␣but␣not␣with␣endpoints␣or␣partitioned␣operations.

228\end{concern}

230%\miniminititle{Existing␣MPI␣mechanisms␣require␣manual

231%intra-node␣collective.}

232With␣existing␣MPI␣mechanisms,␣users␣need␣to␣perform

233the␣intranode␣portion␣of␣the␣collective␣(see

234\figref{fig:collective_compare}).␣For␣example,␣in␣an

235allreduce␣collective,␣the␣user␣needs␣to␣perform

236a␣reduction␣step␣after␣all␣threads␣have␣completed␣the

237internode␣part␣of␣the␣allreduce.␣With␣user-visible␣endpoints

238or␣partitioned␣operations,

239on␣the␣other␣hand,␣the␣collective␣is␣only␣one␣step---all

240threads␣participate

241in␣a␣collective␣of␣the␣same␣communicator␣through

242different␣endpoints␣or␣partitions.␣The␣MPI␣library␣then

243conducts␣both␣the␣internode␣and␣intranode␣parts␣of

244the␣collective␣before␣returning␣from␣the␣operation.

245Although␣the␣performances␣of␣the

246two␣approaches␣are␣yet␣to␣be␣compared,␣we␣note␣that,␣from␣a

247design␣perspective,␣the␣endpoints␣and␣partitioned

248approaches␣are␣better␣because␣they␣do␣not␣force␣the

249user␣to␣manually␣handle␣the␣intranode␣portion␣of

250a␣collective.␣Arguably,␣shared-memory

251programming␣models␣feature␣direct␣support␣for

252collectives␣between␣threads;␣for␣example,

253OpenMP␣supports␣a␣reduction␣operation␣through

254compiler␣directives.␣But␣such␣support␣does␣not

255apply␣to␣all␣types␣of

256collective␣communication␣that␣MPI␣features

257(\eg{},␣\texttt{MPI\_Alltoall}).

258A␣\naive{}␣implementation␣for␣such␣cases␣is␣likely

259to␣hurt␣performance␣for␣high␣thread␣counts␣(relevant

260on␣existing␣and␣upcoming␣many-core␣processors).

261Efficiently␣implementing␣a␣collective

262is␣not␣a␣trivial␣task;␣researchers

263have␣spent␣numerous␣efforts␣into␣optimizing

264collectives~\cite{hoefler2014energy,chan2007collective}.

265Manually␣implementing

266tree-style␣and␣bucket␣algorithms␣is␣a␣tedious␣task␣that

267could␣instead␣be␣handled␣by␣the␣MPI␣library␣as␣is␣the␣case

268in␣the␣user-visible␣endpoints␣and␣partitioned␣operations

269designs.

314buffers␣of␣the␣endpoints␣on␣a␣single␣process

315contain␣the␣same␣values␣(like␣\everywhere{}␣where

316each␣process␣features␣a␣copy␣of␣the␣resulting␣buffer)

317when␣only␣one␣such␣buffer

318is␣needed␣since␣all␣threads␣can␣directly␣read␣from␣the

319single␣buffer.␣With␣communicators,␣on␣the␣other␣hand,␣such

320duplication␣does␣not␣exist.␣For␣example,␣the␣user␣can␣perform

321an␣intra-node␣reduction

322into␣a␣single␣buffer␣that␣all␣threads␣can␣read␣from.

323The␣partitioned␣communication

324interface␣overcomes␣the␣duplication␣issue␣with

325endpoints.

326Each␣partition␣of␣a␣partitioned␣collective␣would

327be␣different␣sections␣of␣the␣input␣buffer.␣With

328threads␣driving␣distinct␣partitions,

329the␣MPI␣library␣would␣implement␣both␣the␣intranode

330and␣internode␣portion␣of␣a␣collective,␣and␣each␣process

331would␣host␣only␣one␣buffer␣that␣contains␣the␣result

332of␣the␣collective.␣We␣note,␣however,␣that␣we␣have␣yet

333to␣identify␣a␣case␣where␣an␣\everywhere{}␣application

334has␣run␣out␣of␣memory␣solely␣because␣of␣duplication

335of␣a␣collective’s resulting data. Hence, the duplication

336of data in collectives with user-visible endpoints is not

337as concerning as the duplication of domain-level

338data that has caused applications to run out of memory

339with \everywhere{}. Furthermore, the duplication

340does not hold for collectives where the result of the

341collective is different for different ranks (\eg{}, alltoall).

348\subsection{Heterogenous computing environments}

349\label{sec:heterogenous_computing}

350

351The discussion in this paper so far has largely been

352in the context of (CPU-initiated) \threads{} communication

353because the performance-oriented studies of the designs

354in the context of accelerators are yet to be conducted.

355Nevertheless, we briefly discuss how the different designs

356compare and apply to heterogeneous computing

357environments. Today’s␣distributed␣applications␣that␣use

358accelerated␣computing␣have␣to␣largely␣rely␣on␣the

359control␣transferring␣back␣to␣the␣CPU␣from␣the␣accelerator

360(\eg{},␣GPU)␣before␣exchanging␣data␣with␣remote␣nodes.

361The␣system␣and␣runtime␣overheads␣(\eg{},␣GPU␣kernel

362launch␣latencies),␣however,␣limit␣the␣parallel␣efficiency

363of␣an␣accelerated␣application.␣One␣way␣to␣combat␣the

364scalability␣issue␣is␣to␣initiate␣communication

365from␣the␣accelerator.␣Technologies␣like␣NVSHMEM~\cite{hsu2020initial}

366and␣ROC\_SHMEM~\cite{hamidouche2020gpu}␣support

367GPU-initiated␣communication␣for␣the␣OpenSHMEM~\cite{chapman2010introducing}

368programming␣model.␣GPU-initiated␣(point-to-point)

369MPI␣communication,␣however,␣remains␣an␣open␣problem.

370Executing␣MPI’s matching engine

371on the GPU is known to be expensive~\cite{klenk2017relaxations}.

372

373\begin{concern}

374 \emph{Lesson 20:} Partitioned operations

375 provide lightweight interfaces for device-initiated

376 communication; the other two designs do not.

377\end{concern}

378

379Out of the three designs, partitioned operations are best

380suited for high-speed device-initiated point-to-point operations.

381Through its non-critical-path \texttt{P[send|recv]\_init}

382APIs, partitioned communication enables most of the serial

383overhead of setting up a low-level network message to be

384executed on a low-latency CPU core (before kernel launch)

385rather than a high-latency GPU compute unit. GPU thread

386blocks

387would then trigger or check for arrival of partitions with

388the lightweight \texttt{Pready} and \texttt{Parrived}

389operations~\cite{pcaccelbindings}. Nonetheless, the

390limitations of partitioned operations described in Lessons

39114 and 15 apply to heterogeneous computing scenarios as

392well---program control would need to return back to the CPU

393(\eg{}, to execute an \mpiwait{}) before the GPU

394can issue the next partitions of a message. Such repeated

395transfers of control will re-introduce device runtime

396overheads that device-initiated communication aims to

397address in the first place. Extensions that enable MPI

398operations to be enqueued into accelerator’s␣work␣queues

399(similar␣to␣Nvidia’s NCCL runtime~\cite{nccl}) may reduce such

400runtime synchronization overheads. These extensions,

401however, could apply to existing MPI objects and

402user-visible endpoints too.

403

404Another way for applications to combat the device

405runtime overheads that hurt scalability is to use

406persistent GPU kernels that offload

407communication operations to the faster CPU cores

408through lightweight atomics or flags. How such an

409approach compares to device-initiated communication

410remains to be seen. Such application-level techniques

411are promising given the move towards system

412architectures with tightly integrated CPUs and

413GPUs where the latency to communicate between

414the two types of PUs will diminish~\cite{gracehopper, vijayaraghavan2017design}.

415

416Furthermore, the benefits of device-initiated

417communication either compared to or in conjuction

418with techniques that leverage smart NICs or network

419hardware tag matching remains to be seen. All in

420all, the lessons from this paper remain relevant

421for heterogeneous computing environments

422moving forward.

## IV Meeting the Needs of Domain Scientists

”Rule of thumb for UX: More options, more problems.” — Scott Belsky

TABLE I: Summary of design choices to expose logically parallel communication (TBD: to be defined).

| Operation | Existing MPI mechanisms | User-Visible Endpoints | Partitioned Communication |
| --- | --- | --- | --- |
| Point-to-point | Communicators or tags | Endpoints | Partitioned point-to-point APIs |
| RMA | Window(s) | Endpoints | Partitioned RMA APIs (TBD) |
| Collective | Communicators + user-driven intra-node collective | Endpoints | Partitioned collective APIs (TBD) |

Table I shows a summary of the design choices to expose logically parallel communication for different types of MPI operations. With existing MPI mechanisms, users have to be aware of a multitude of options since each mechanism does not uniformly apply to all communication types and patterns. Domain scientists need to be aware about the mechanisms that become available when hints relax different semantics. Furthermore, each mechanism poses unique challenges: using communicators is hard because of MPI’s matching semantics; the optimal use of tags is highly dependent on MPI implementation-specific hints; windows may not allow users to optimally expose the available communication independence. The new partitioned communication interface also poses challenges to the user. The new semantics of partitions and the large expansion in MPI’s API space indicate a multitude of options for the user to learn about and choose from. The interface is challenging to use for dynamic and irregular communication patterns especially those that use wildcards. More important, the semantic limitations of the interface prevent the user from achieving complete independence between threads. One way to combat the limitations of the interfaces in MPI 4.0 is to design an abstraction on top of MPI that allows users to seamlessly expose communication independence in a user-friendly manner. The abstract layer would then use MPI 4.0 mechanisms underneath with MPI-implementation specific hints where needed (analogous to how different interconnects support the Open Fabrics Interfaces (OFI) [35] API through their own OFI providers). The challenge of such an abstraction is the design of an interface that applies to all communication patterns. The interface of user-visible endpoints is in fact an example of such a general abstraction; other forms remain to be investigated. But, more important, the implementation of any abstraction faces the semantic constraints of both existing MPI mechanisms (e.g., matching semantics of communicators) and partitioned operations (e.g., no wildcards). In contrast, with user-visible endpoints, the interface that has not been standardized yet, users need to be aware of only one mechanism: endpoints, which applies uniformly to all types of MPI operations. Endpoints provide a flexible, straightforward interface for users to express logically parallel communication in a way that they are already familiar with (i.e., using ranks). The concern with user-visible endpoints is a misimpression among domain experts about what endpoints represent. A reason for this is that the terminology in the MPI Endpoints proposal is oriented towards the community of MPI library developers. Since the ultimate goal of the proposal is to aid the domain scientist to express logically parallel communication, it is imperative that the proposal be user-facing. To resonate with domain experts, we suggest rebranding111Rebranding techniques have proven to be successful with many technologies (e.g., Android, Airbnb, etc.). the proposal to MPI Rankpoints since it emphasizes that users can create multiple MPI ranks within a process. The goal is to educate and reinforce the understanding that rankpoints are not handles to network resources, rather they are a flexible, straightforward means of expressing parallelism that promotes portability of applications. While it requires one new API—MPI_Comm_create_rankpoints—it prevents the limitations of existing MPI mechanisms and partitioned operations. Rebranding is more than just a change in the name of the proposal. It requires a concerted effort by the MPI community in re-education through venues such as presentations and tutorials at flagship conferences and workshops.

## V Concluding Remarks

”People ignore design that ignores people.” — Frank Chimero MPI+threads is a critical model to program the many-core processors of the current HPC clusters and the upcoming exascale systems. It is imperative that applications perform productively with it. The key to achieving high performance with MPI+threads requires effort from both MPI library developers and application developers. Recently, MPI libraries have made significant strides in this regard, and now the ball is in the court of domain scientists to expose communication parallelism to utilize the new fast MPI+threads libraries. Domain scientists, however, face many programming challenges (Lessons 1–5, 7–9, 14–16, 18) with the designs present in MPI 4.0 with respect to exposing the communication independence between threads. These solutions have their own merits (Lessons 6, 13, 20), but we show that they do not meet the needs of key communication patterns sufficiently. The MPI Rankpoints alternative, on the other hand, elegantly addresses the various limitations of the designs in MPI 4.0. MPI Rankpoints has its own challenges (Lessons 17 and 19), but its benefits (Lessons 10–12, 16, 18) prove to be a seamless option for domain scientists given that the design applies generally to all communication patterns. The lessons in this paper show that MPI Rankpoints, or a solution that is as flexible, warrants continued consideration as a viable solution for the MPI+threads programming model.
